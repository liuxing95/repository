# Obsidian 知识库：资料采集、版本关联与课题生成

**日期：2026-09-20｜性质：对技术方案 v1.0 的补充设计，不是已经实现或部署的功能**

本文回答三个实际问题：资料怎么进库；多份资料怎样形成可靠关联；给出一个研究课题后，怎样选择材料并生成有出处、不过度泛化的内容。以 Vite、esbuild、Rollup、Rolldown、Oxc 为贯穿案例。

## 1. 先明确原方案的能力边界

现有《Obsidian-KB-Technical-Spec-2026-09-20.md》§0.2、§6 已将 V1 输入收敛为 UTF-8 Markdown/TXT，以及 Web Clipper 保存的 Markdown。默认由用户点击“导入选中资料”；URL 是来源元数据，不触发服务自动抓取。PDF、仓库连接器和服务端网页抓取被放到后续阶段。

该文 §7 已有固定快照、主张提取、实体别名、来源反向依赖和增量提案；§8 已有词法检索、版本过滤与有引用的问答。但完整的“课题自动拆解—分版本采集—证据覆盖—逐节生成”尚不是一个已定义完整的研究工作流。本补充把它具体化，不把这些能力描述成安装 Obsidian 即可获得。

**推荐分层：** 人决定研究目标和权限；采集器获得可追溯原文；模型提出主张与关联；程序校验身份、范围和引用；人复核关键语义；研究器按问题取证，再组织文章。

## 2. Vite 案例：为什么只贴版本标签仍然不够

本轮查询官方材料得到以下有限范围的事实：

| 范围 | 依赖预打包/优化 | 生产打包 | 说明 |
|---|---|---|---|
| Vite 7 文档描述的普通 `vite` 路线 | esbuild | Rollup | 不能概括成“生产也由 esbuild 打包” [V1][V2] |
| Vite 7 的 `rolldown-vite` 技术预览路线 | Rolldown | Rolldown | 包分发和配置路线与普通 `vite` 不同；不能只看大版本 [V3] |
| Vite 8.0 正式发布的路线 | Rolldown | Rolldown | 2026-03-12 发布公告确认统一 bundler；转换环节另涉及 Oxc [V4][V5] |

esbuild 官方说明其实现使用 Go；Rolldown 官方说明它是 Rust-based bundler。[V6][V7] 这描述的是两个工具的实现语言，不是两种语言“实现了不同版本的整个 Vite”。

Vite 8 迁移文档还保留了部分旧配置的兼容转换，也说明特定插件或兼容路径可能需要自行安装 esbuild。[V5] 因而“源码或文档出现 esbuild 字符串”与“默认依赖优化器仍是 esbuild”不是同一个判断。

上表是文档级架构说明，不是对每个补丁版本和第三方插件组合的运行证明。要解释一个实际项目，须固定真实解析包、版本、配置及插件，再做对应核对。

### 2.1 每条技术主张需要的上下文

推荐至少记录：实体、版本范围、分发包/实现路线、功能阶段、配置条件、状态/语气、证据。

例如不能只存：

```text
Vite → uses → esbuild
```

而应存为两个彼此独立的主张：

```text
主张 A：Vite 7 普通包，在默认开发依赖预打包环节使用 esbuild。
主张 B：Vite 7 普通包，在生产打包环节使用 Rollup。
```

Vite 8 的主张另行保存，不覆盖 A、B 的历史适用性。[V1][V2][V4]

## 3. 用户实际怎样收集和录入

### 3.1 随手收藏：先保留材料，不要求你先组织整张图

使用流程设计为：浏览资料 → 剪藏到 `00-Inbox` → 选中一份或一批 → 检查来源卡 → 确认导入。

来源卡只要求用户确认最少信息：正文是否覆盖需要的内容、来源身份是否正确、是否允许发给所选模型。主题和版本可留空，系统稍后提出候选。允许留空比为了入库强行猜一个版本更安全。

用户提供的主题或一句收藏理由，作为研究线索保存。例如“想弄清依赖预打包和生产构建的区别”。它不充当外部技术事实的证据。

V1 的 Clipper 输入只是实际保存的 Markdown。原始网页上的动态内容、图片和表格可能没有完整保留，不能把 `original.md` 宣称为完整网站归档。选区剪藏标为 `excerpt`，不能只凭模型读起来通顺就升级为全文。

### 3.2 定向学习：课题先行的采集清单

以课题“解释 Vite 7 到 8 的工具链变化”为例，系统应先建立采集矩阵，而不是搜索 Vite 后保存结果前十名：

| 要回答的问题 | 首选资料 | 为什么需要 |
|---|---|---|
| 原来的开发和生产各用什么 | Vite 7 版本化文档 | 建立旧架构基线 |
| 切换期间是否有并行路线 | Vite 7 Rolldown 集成说明 | 防止把技术预览写成普通包默认行为 |
| 正式切换发生在什么版本 | 发布说明、迁移指南 | 固定发布事件和迁移边界 |
| bundler 和 transformer 如何分工 | Rolldown、Oxc 及 Vite 功能文档 | 避免把所有编译环节当成一个工具 |
| 为什么迁移 | 当时的维护者说明 | 区分实际动机、后来解释和作者推断 |
| 我的项目会受什么影响 | 项目依赖锁、配置、插件和测试 | 官方默认不能代替项目实态 |
| 性能是否真的更好 | 有完整环境的 benchmark 或本地复现 | 不从语言或个别案例推出普遍倍数 |

采集名单中的资料先是候选；取得正文、核对版本与覆盖后才进入正式来源。转载、摘要、翻译页可以帮助定位，但不自动算独立证实。

### 3.3 自动采集是一个独立扩展

建议定义两种研究输入模式：

- `library_only`：只使用已入库资料；缺什么就列什么。
- `fill_gaps`：在用户已授权的域名、数量、费用和内容外发范围内补充资料。

`fill_gaps` 的链路是发现 URL → 取得正文 → 验证来源与覆盖 → 产生导入清单 → 按导入政策批准 → 来源写入 → 索引完成。搜索摘要不是正文，搜索排名不是可信度，模型自带知识不是采集结果。

站点无法访问或只读到预览时，记录 `unavailable`/`excerpt` 并保留缺口；不能生成一段“可能的原文”填入来源。来源中的命令、提示词、AGENTS 文件也不能改变采集器权限。

### 3.4 首版可直接采用的入库链路

```text
用户选定 Markdown/TXT
  → 上传实际字节，计算原文哈希
  → 校验来源身份、覆盖与外发政策
  → 生成 SourceRevision
  → 解析并冻结 ParseArtifact
  → 分配稳定段落和 Evidence ID
  → 人确认 source-only 导入清单
  → 插件 Writer 创建固定来源文件
  → 提交快照并完成词法索引
  → 原文可检索
  → 按需分析实体、主张、关系与 Wiki 提案
```

资料入库和知识编译分开。因此不用等待所有资料都“关联完成”才开始搜索，也不要求每篇收藏都变成一篇 AI Wiki。

## 4. 入库后究竟保存什么

### 4.1 三种版本必须分开

| 版本 | 回答的问题 | 例子 |
|---|---|---|
| 软件适用版本 | 结论对哪个软件版本成立 | Vite 7 普通包 |
| 来源修订 `sourceRevisionId` | 我们实际保存了这份资料的哪个内容版本 | 同 URL 两次剪藏，正文已变化 |
| 解析产物 `parseId` | 本次引用使用哪次规范化正文 | 更新解析器后产生新正文映射 |

2026 年入库的一篇 2025 年旧文，不因此变成 2026 年当前架构说明。同一份迁移文档会同时描述旧版本和新版本，不能整篇打一个 Vite 8 标签后，让其中所有句子都变成 Vite 8 事实。

### 4.2 来源卡与主张卡分离

来源卡记录事实来源：URL、标题、作者/维护者、捕获时间、发布或更新时间（未知保留空）、内容哈希、覆盖情况、来源家族、许可读取与模型路线。

主张卡记录技术含义：谁，在什么版本和配置下，哪个阶段，使用什么组件，主张的语气是什么，具体由哪些原文支持。

一个来源可产生零条或多条主张；一条主张也可以由多个来源共同支持。原文是证据对象，摘要是辅助表达，二者不能相互替代。

### 4.3 一个示意记录

以下为根据官方文档手工示意的数据形状，`example-*` 是示例 ID，不是本轮已导入真实知识库的记录；未声称读取到具体发布包 commit。

```json
{
  "claimId": "example-vite7-dep-prebundle",
  "subjectEntity": "npm:vite",
  "predicate": "uses_for",
  "objectEntity": "npm:esbuild",
  "scope": {
    "softwareVersion": {
      "kind": "documented_major",
      "major": 7,
      "basis": "versioned_documentation"
    },
    "distribution": "standard-vite",
    "phase": "dependency-prebundle",
    "mode": "development",
    "configuration": "default",
    "modality": "documented_behavior"
  },
  "evidenceIds": ["example-v7-doc-evidence"],
  "scopeReview": "requires-verification-on-import"
}
```

`documented_major` 只表示文档声明范围；不能自动转为“已测试所有 7.x 补丁”。精确项目核对应增加 resolved package、精确版本、配置摘要及测试环境。

### 4.4 不修改原文来消除歧义

原文“现在已经换成它”不能直接改写为“Vite 8 已改用 Rolldown”。应单独生成 `contextHints`：候选实体、候选版本、解析依据和未解决歧义。检索可以使用这些附加线索，引用仍指向原文。

无法确定“现在”对应哪一天，或“它”是哪一个组件时，保留 `unknown`。入库日期和模型训练知识都不能替代来源语境。

## 5. 怎样判断资料之间有关联

### 5.1 先区分导航关联与事实关系

**导航关联**说明值得放在一起学习：同一课题、共用实体、引用了彼此、讨论相近问题。可以用于推荐阅读、双向链接和候选召回。

**事实关系**说明资料支持什么结论：组件使用、实现语言、默认后端、版本替换、反证、条件限制。要进入回答的事实推导，必须有明确谓词、适用范围和证据。

例如两篇文档都提到 Vite 和 Rolldown，只足以提名“可能相关”；不能直接确认“一份证明另一份”。

### 5.2 关联流水线

```text
抽取实体提及和候选主张
  → 用软件包、仓库、已核对别名匹配实体
  → 找相同实体/主题/引用的候选资料
  → 检查候选主张的谓词与适用范围
  → 返回关系类型及依据
  → 确定性验证引用和身份
  → 关键关系进入审核
```

实体身份优先使用稳定的软件包和仓库标识。标题与向量相似仅用于候选检索。`Rollup` 与 `Rolldown` 不是别名；`vite` 依赖名也可能通过 package alias 指向其他实际包，因此项目识别应看解析结果，而不只看声明名称。

V1 可以先靠实体别名、精确符号和词法召回做候选发现；向量是可选增强，不是事实关系验证器。候选关联允许漏一些，以后补充；重要事实边不能为了“图更密”而强行建立。

### 5.3 关系类型建议

| 类型 | 含义 | 可直接作为外部事实依据吗 |
|---|---|---|
| `same_topic` | 都服务某个学习课题 | 不可以 |
| `mentions` | 某段原文提及实体 | 只能证明被提及 |
| `learning_prerequisite` | 为学习安排建议先读 | 不是运行时依赖 |
| `uses_for` | 某组件在指定阶段使用另一个组件 | 有范围与证据时可以 |
| `implemented_in` | 某组件的实现语言 | 仅适用于该组件 |
| `supports` | 某证据支持一条主张 | 还需检查条件和语义 |
| `contradicts` | 同范围内出现互斥结论 | 须范围重叠且谓词允许互斥判断 |
| `qualifies` | 为主张补充条件或例外 | 必须连同条件呈现 |
| `replaces_for_scope` | 一个路线在特定范围替换另一个 | 不能抹掉历史事实 |
| `derived_from` | 摘要、转载或翻译来自同一材料 | 用于来源家族去重，不是新增证据 |

### 5.4 不允许任意传递关系

```text
Vite --uses_for(dependency-prebundle, scope...)--> esbuild
esbuild --implemented_in--> Go
```

不能按通用图遍历推出 `Vite --implemented_in--> Go`，也不能推出“研究 Vite 必须先学完整 Go”。前者混淆谓词，后者混淆实现依赖与学习先修。关系推导只使用明确批准的有限规则；没有规则的路径只用于发现材料。

## 6. 多版本资料如何共存而不污染结论

### 6.1 冲突判断使用三值范围匹配

比较两条主张前，计算软件版本、包分发、功能阶段、配置、运行环境、时间及语气是否重叠。结果是 `overlap`、`disjoint` 或 `unknown`，不强行压成布尔值。

只有范围已知重叠、谈同一主体与谓词，且结果确实互斥时，才进入“矛盾候选”。“使用 A”与“使用 B”本身未必矛盾，一个流程可以同时使用多个组件。默认单一后端这类明确互斥的位置才适合机械发现冲突。

| 两条记录的差异 | 处理 |
|---|---|
| 软件版本不重叠 | 版本演进；分别保存 |
| 普通包与技术预览包不同 | 实现分支；分别保存 |
| 开发预打包与生产打包不同 | 阶段分工；分别保存 |
| 默认值与自定义插件配置不同 | 条件/例外；不可互相覆盖 |
| 计划采用与已经发布不同 | 路线图与已交付事实分开 |
| 版本或配置未知 | 标为需要范围确认，不假定冲突或一致 |
| 同一已知范围内给出互斥默认值 | 冲突候选，找准确版本的证据核验 |

### 6.2 不按“发布时间更新”裁决一切

检索时优先检查适用性，再比较证据。当前官方说明不一定适用于旧软件；旧版本官方文档可能是回答旧项目的恰当来源。来源级权威性、版本匹配、是否直接观察、覆盖完整度和可复現条件应分别保存，不压成一个自报可信度分数。

一篇正确转述官方文档的博客和五篇同文转载，不构成六份独立实证。一次局部测试也只证明测试过的环境，不证明所有平台和配置。

### 6.3 正面与负面结论的证明强度不同

“存在一种支持方式”可以由具体实现或实例支持；“任何情况下都不支持”“已经彻底移除”要求更完整的范围证据。源码里搜索不到某个词，不直接等于功能不存在；依赖列表有某个包，也不直接等于它是默认执行路径。

特别是兼容 API：Vite 8 文档中的旧字段和 esbuild fallback，需要解释它们的角色，不能用字符串共现重建旧架构。[V5]

### 6.4 更新是失效提示，不是全库覆盖

新来源修订进入后，按 `SourceRevision → ParseArtifact → Evidence → Claim → PageRevision/ResearchOutput` 找直接受影响对象。区分三类动作：来源有变化待复核、历史事实仍有效但不适用于新版本、原结论被直接纠正。

旧版本的正确主张保留。新的当前架构页或演进页另行提出修改。只更新受影响内容，不对整库无界重编译。已导出的文件不可能被系统远程改写；系统只能标记所记录的报告版本需更新，并生成新版本候选。

## 7. 准确性保障到底能做到哪一层

### 7.1 可机械检查的约束

原文及对象哈希一致；引用 ID 存在；摘录能回读；被引用来源未撤回；已核定范围没有被错误混装；没有越权外发；生成内容只引用允许的证据；不同来源家族没有被重复计数；未经批准不写正式 Wiki。

这些可以做强测试。但范围元数据本身也可能抽取错误，因此“范围检查通过”的保证以范围已正确核定为前提。

### 7.2 仍需语义判断的部分

原文是否真的支持结论；来源有没有遗漏条件；作者是在报告事实、预测还是发表意见；某个代码分支是否是默认路径；新旧资料是否真的矛盾；性能实验能否推广到自己的项目。

可用独立验证步骤和人工抽检降低风险，但另一个模型不是自动正确的裁判。`reviewed` 表示完成某个审核流程，不表示不会出错。

### 7.3 系统应给出的诚实状态

结果至少区分 `supported`、`insufficient_evidence`、`conflicting_evidence`，并另外显示适用范围、资料检查时间、完整性与待核验问题。无法确认当前状态时，只输出“截至库内所核验资料”的限定结论，不假装拥有实时全网知识。

## 8. 给出一个课题后怎样查询并生成

### 8.1 课题合同

以“Vite 构建工具链的演进：esbuild、Rollup、Rolldown 的分工”为例，研究任务先保存：目标读者、输出类型、范围、版本/路线、核查截止时间、仅库内还是允许补资料、是否需要代码复现、必须覆盖的问题和总预算。

要区分四种时间意图：解释指定软件版本；描述现在的状态；比较版本演进；重建某个历史日期当时可以知道什么。最后一种还要过滤来源公开时间。今天的迁移指南可以解释旧版本，但不能伪装成当时已经公开的知识。

未指定版本且问题是一般学习时，可以生成明确分版本的概览；涉及项目行为时，读取用户授权的锁文件和配置确定目标，不从文章发布时间猜项目版本。

### 8.2 先拆问题，不直接要求模型写长文

示例研究问题为：旧版开发预打包和生产打包如何分工；技术预览与普通包有什么不同；正式切换版本是什么；bundler 与转换器怎么协作；迁移动机有哪些一手证据；有哪些兼容路径；性能结论的测试范围是什么。

这些问题生成采集清单和检索计划。正文目录可以先有草案，但最终目录必须根据证据覆盖调整，不能先写出结论后找引文装饰。

### 8.3 每个子问题独立检索

```text
绑定研究身份与内容权限
  → 解析实体、目标版本、包分发、阶段
  → 从实体/来源目录定位候选
  → 在各个子问题和版本桶内召回
  → 查关键词、代码符号，必要时有限关系扩展
  → 检查适用范围和反证
  → 来源家族去重
  → 读取固定原文及上下文
  → 形成章节证据包
```

V1 的“最多 8 个 evidence blocks”是一次回答的上下文限制，不能直接当成一篇多章节报告的全局资料配额。研究任务按章节分别取证，每个子调用继续遵守原有输入/输出上限；顶层必须另设并执行总调用和费用预算，不能通过拆子任务绕过预算。

不先把全库私密文本交给云端 reranker 再过滤。权限、外发路线、撤回状态适用于候选、原文读取、重排、证据包和生成的每一阶段。

### 8.4 按覆盖而不是按总命中数判断资料够不够

| 子问题 | 需要的证据 | 缺失时的行为 |
|---|---|---|
| Vite 7 普通路线 | 准确版本的预打包、生产说明 | 不用 Vite 8 当前文档替代 |
| 技术预览分支 | rolldown-vite 的范围与版本信息 | 不推断“所有 Vite 7 都一样” |
| Vite 8 正式切换 | 发布说明、迁移说明 | 保留未确认的发布日期/边界 |
| Rust/Go 的角色 | 组件自己的实现说明 | 不推断整个上层系统的语言 |
| 性能因果 | 环境、版本、输入、配置、测量方式 | 输出机制分析，明确没有完成同条件比较 |

检索返回 50 篇也可能仍缺少其中一格。每个主要问题需要有足够直接证据或明确缺口；不能用大量同主题背景资料掩盖核心证据不存在。

### 8.5 缺口补采与快照推进

`library_only` 模式立即给出缺口和可写范围。`fill_gaps` 模式只围绕缺口补采，在配置的轮数、文档数和总预算到达后停止。

新资料必须完成导入和索引，随后显式从研究快照 A 推进到 B，重取受影响证据包。最终生成时冻结同一个研究快照；不能部分章节用 A 的元数据、另一部分偷偷读取当前磁盘的新正文。

来源覆盖不足不必拒绝整篇：可以写已支持的章节，缺失段落明确保留“待验证”，但不能给出无证据的迁移建议或性能倍数。

### 8.6 章节 EvidencePack

每个章节的证据包包含：子问题、目标范围、可用主张、原文片段及上下文、支持/反对/限制关系、来源版本、状态和警告。初稿只从这些包组织重要技术结论。

```text
章节：Vite 7 默认路线
适用：普通 vite 包、文档说明的默认配置
可用证据：预打包说明、生产构建说明
必须保持：开发阶段与生产阶段分开
不得推出：整个应用开发阶段全部被 esbuild 打包
不得推出：所有同大版本分发包都采用相同工具链
缺口：未对用户实际插件组合做运行验证
```

学习写作中的类比、解释和推导可以加入，但须区分来源直接陈述与作者推理。引文不是用来给模型先验结论盖章的。

### 8.7 先逐节写，再全局核对

逐节生成后，做整篇主张审计：每个核心结论对应哪份证据；有没有从默认扩大到全部；有没有丢版本、否定、条件和语气；是否把不同阶段混成同一实现；是否把组件依赖当实现语言；是否把 benchmark 案例写成普遍定律。

结构验证只能验证引用存在，不能验证语义必然成立。重要争议、迁移建议、未经复现的性能判断需要独立阅读原文或人工复核。检查失败时回到取证/改写，达到预算上限就保留不足说明。

### 8.8 输出与沉淀

建议研究结果包含正文、来源与版本清单、证据覆盖表、未解决问题、研究清单（snapshot、查询、模型/提示版本和成本）。这些使后续更新有依据，不要求普通读者阅读全部运行日志。

默认生成候选报告，按现有规则保存在 `50-Queries` 或审核工作区；人工项目目录 `40-Projects` 仍默认自动化只读。人选择保留时通过批准写入；要把结论提升为 Wiki，还要重新去重和检查证据。

研究报告是派生产物，不成为新的独立外部事实源。下一次研究应沿它的引用回到原始资料。

## 9. Obsidian 中如何呈现关联

实体页、版本页、机制页和研究报告页分工：实体页负责导航；版本页说明特定分发和版本；机制页讲预打包/转换/生产打包等概念；研究报告页组织某一次课题的结论。

示意布局：

```text
20-Wiki/systems/Vite.md
20-Wiki/systems/Vite-7-默认路线.md
20-Wiki/systems/Vite-7-Rolldown-技术预览.md
20-Wiki/systems/Vite-8-工具链.md
20-Wiki/concepts/依赖预打包.md
20-Wiki/concepts/生产打包.md
20-Wiki/concepts/语法转换.md
```

不必为每个包的每个补丁建立页面；精细范围保存在主张和证据元数据，只有足够重要的变化才成为独立版本页。Obsidian 链接图是导航投影，不承担真假和范围判断；事实边保存在 SQLite 及 provenance 中。

页面可展示“当前说明”“历史适用”“来源已更新待复核”等提示。AI 不得通过自行修改 frontmatter 把资料状态或发布权限升级。

## 10. 需要补到 TypeScript 方案的模块

以下是建议新增的设计边界，不是已经存在的 API 或代码。

| 模块 | 输入 | 输出 | 关键限制 |
|---|---|---|---|
| `CollectionPlanner` | 课题、范围、现有来源目录 | 采集问题矩阵和候选入口 | 不自行修改权限，不把检索摘要当来源 |
| `SourceProfiler` | 固定 ParseArtifact、来源元数据 | 实体提及、文档类型、版本候选 | 不确定范围保留 unknown；不修改原文 |
| `ClaimRelationResolver` | 主张候选、实体目录、相关证据 | 带范围的关系与冲突候选 | 相关不等于支持；重要边需证据 |
| `ScopeEvaluator` | 请求范围、主张范围 | overlap/disjoint/unknown 及解释 | 不按发布时间猜软件版本 |
| `ResearchPlanner` | 研究请求与候选材料 | 子问题、章节和覆盖需求 | 多章节不是一次 top-k 问答 |
| `EvidencePackBuilder` | 子问题、授权快照、召回结果 | 支持/限制/反证包和缺口 | 固定原文与版本；预算和 ACL 前置 |
| `ResearchWriter` | 证据包与章节计划 | 带主张映射的报告草稿 | 重要事实不能由模型记忆补空 |
| `ClaimAuditor` | 草稿、证据包、范围规则 | 阻断项、待复核项、修订建议 | 不把第二个模型当绝对正确裁判 |

这些先是服务内模块，不增加新的微服务或数据库。实体、别名、主张范围与关系可以使用 SQLite 表；主张数据与原始来源通过证据关系连接。

研究任务可以采用如下设计接口：

```text
POST /v1/research-jobs
  topic / scope / sourceMode / requiredQuestions / budget
  → jobId

GET /v1/research-jobs/:id
  plan / coverage / gaps / sourceManifest / outputs / usage

POST /v1/research-jobs/:id/save-proposal
  outputId
  → ChangeSet 候选
```

`fill_gaps` 还需要真正实现受控采集器及权限，不是加一个枚举字段就可以上线。保存和批准继续使用原有写入协议，不开新的旁路。

## 11. 应先建设哪些能力

第一阶段把来源版本、文档覆盖、主张范围和精确检索做好；第二阶段完善实体与有限关系；第三阶段实现库内研究规划、逐节取证和报告审核；第四阶段才接课题缺口自动采集。这样即使抓取扩展未完成，用户仍可用 Clipper 导入，完成高质量库内研究。

对当前 V1 的具体调整建议：E06 增加来源元数据与段落级范围候选；E09 增加关系类型和范围三值判断；E07/E10 增加按版本/分发/阶段取证和结论范围校验；在 E10 后另建研究任务，而不是把多章节长文硬塞进原单问上限；网页采集继续作为显式扩展。

新增工作量应另行估算，不将它们暗算为原 E00—E14 计划已经完成的范围。

## 12. 用哪些测试证明没有把版本混在一起

以下是应实现的回归用例，本次未运行知识库系统：

| 输入/提问 | 必须观察到的行为 |
|---|---|
| 只有 Vite 7 普通包资料，问其生产 bundler | 不把开发预打包的工具当生产 bundler |
| 同时有普通包与 rolldown-vite 文档 | 两种路线分别呈现，不因同大版本直接合并 |
| 一篇迁移指南同时描述 before/after | 每个主张独立绑定对应范围 |
| 同时有旧版与新版文档 | 不按导入日期覆盖历史适用事实 |
| 只有实现语言资料，问迁移快多少 | 说明缺少同条件性能证据，不编倍数 |
| 新文档保留旧配置名 | 不从配置字符串推出默认底层实现 |
| 五篇文章实为同文转载 | 不当成五份独立支持 |
| 无日期文章说“现在支持” | 当前版本主张保持 unknown，不能静默补版本 |
| 技术预览说明“未来计划” | 不记成已经正式发布 |
| 问“当时已知什么” | 不把后来才出现的文档当成当时的公开证据 |
| 研究中追加来源 | 显式推进快照并更新证据包，不混读版本 |
| 多个研究子任务并行或串行 | 顶层总预算仍生效，不能拆分绕过 |
| 来源撤回、旧报告仍有缓存 | 读取和再生成检查撤回，报告标记需复审 |

对检索评测，应按软件版本和路线分别标注正确证据；对生成评测，应测“有根据但丢了条件”的错误，不能只检查引用链接是否存在。
