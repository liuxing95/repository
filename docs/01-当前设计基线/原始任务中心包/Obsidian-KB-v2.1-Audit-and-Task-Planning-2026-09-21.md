# Obsidian 知识库 v2.1：整体审查、任务管理与自动协调方案

**日期：2026-09-21｜版本：2.1｜状态：设计基线候选，未部署｜主要实现语言：TypeScript｜默认时区：Asia/Singapore**

> 本文收敛前几轮的知识库设计，并新增个人任务、学习计划、进度反馈和提醒。它不是已安装的插件，也不是已运行的服务。本文在已有 v2 草稿上继续核对和修订；不修改历史文档、真实任务或 Library 原文件。本次没有读取或修改真实日历、Todoist 待办或 Obsidian Vault，没有创建任何提醒。
>
> 阅读重点：第 1–3 节回答现有方案的问题；第 4–6 节确定插件与数据归属；第 7–12 节定义任务、协调、同步和提醒；第 13–17 节给出实施与验收；第 19–22 节补充重试、计划提交、提醒一致性和具体落地决策。附录的配置和接口属于本项目设计，不是 TaskNotes 可直接导入的配置。

## 0. 结论与决策摘要

推荐主线：**Obsidian + TaskNotes + 现有 Knowledge Bridge 的扩展 + TypeScript 知识/计划服务**。不要重写任务列表、看板和 Markdown 编辑器，也不要把普通待办与后台抓取作业混成同一类任务。

长期使用闭环为：

```text
资料集合 → 固定来源与证据 → 有范围的知识 → 学习目标 / 研究课题
                                      ↓
                              可执行个人任务
                                      ↓
                      日计划 → 执行 → 产物 / 反馈
                                      ↓
                       复习安排 / 知识修订候选
```

自动收录负责减少搬运；研究负责组织证据；个人任务负责安排人的行动；学习记录负责描述掌握的证据。任何一个环节的成功都不自动代表其他环节成功。

新增任务后默认自动**计算**安排并展示差异。启用可信设置中的受限授权后，才自动**应用**当日、未开始、未锁定的弹性任务安排。修改硬截止时间、跨天挪动、移动有参与者的会议、扩大资料外发和删除来源仍需明确批准。

如果要求电脑关闭后仍能每日提醒，必须有独立在线提醒执行端或外部任务/日历服务；纯本地插件不能独立满足这一部署条件。即使使用远端提醒，也必须明确它持有的是哪个版本的任务状态。

### 2.3 不应删除的原有约束

继续保留：模型不是授权主体；来源输入不能改系统政策；人工笔记默认只读；不以时间戳代替来源版本；不把摘要当原件；模型费用未知时保守记账；取消请求不保证远端停止计费；插件离线不由服务绕过受控路径写 Vault；任何发布及来源清除都有独立流程。

### 2.4 设计基线替换规则

建议把本文作为下一次开发的统一基线。正式接受这份设计后，以下规则优先于历史文档的冲突条款；未列冲突的证据、安全和恢复规则继续继承：

| 领域         | v2 生效规则                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------- |
| 首版输入     | 网页、限定文档集合、固定代码快照和文字型 PDF 均在真实使用范围；复杂解析允许有覆盖说明地降级 |
| 资料学习关系 | 资料全量可索引，但不自动把所有页面转为个人任务或已掌握知识                                  |
| 用户任务     | TaskNotes 任务记录 + 本系统稳定 taskId 和审计投影；不是抓取 job                             |
| 写入         | 一个 Bridge 作为本系统自动化入口，按域调用不同适配器；禁止服务直接改活动 Vault              |
| 计划         | PlanRevision 是本系统排期事实，TaskNotes 任务字段是任务事实，日记中的表格只是投影           |
| 提醒         | 由实际部署的通知执行端运行，不依赖本次对话继续在线                                          |
| 自动化       | 默认 propose；受限委托需通过可信设置开启，不由模型或材料 frontmatter 授权                   |

旧合同不能只改几个接口名继续沿用。实施前建立 schemaVersion、字段迁移和兼容测试；未知版本的数据进入只读诊断，不自动猜测。

## 3. v2.1 系统范围：五个能力域、一个运行底座

```text
统一材料入口
  └─ 摄取域：发现 / 获取 / 原件 / 解析 / 覆盖 / 来源快照
        └─ 知识域：实体 / 范围 / 主张 / 证据 / 检索 / Wiki
              ├─ 研究域：问题拆解 / 取证 / 缺口 / 分节生成 / 审核
              └─ 学习域：目标 / 单元 / 尝试 / 实验 / 复习
                    └─ 行动域：待办 / 依赖 / 可用时间 / 排期 / 反馈

共用：身份、政策、预算、对象仓、持久作业、审计、备份
展示：Obsidian + TaskNotes + Knowledge Bridge 的 Today/Review 界面
通知：本地通知；必要时独立在线 Reminder Relay + 推送渠道
```

不新增通用多 Agent 平台，不重做实时协同编辑，不把任务列表复制到多个互相覆盖的后端。多人日历写入、全站无界爬取、自动替用户修改学习结论仍不在默认范围。

## 4. 插件选型：优先 TaskNotes，别一次安装三套任务引擎

### 4.1 主选 TaskNotes

维护者说明 TaskNotes 使用一任务一 Markdown 文件、YAML properties 和 Bases 视图，提供任务列表、看板、日历及时间记录等能力；任务字段可扩展，适合链接课题和资料。[S01]

本系统复用它的任务创建、编辑、看板和计时，不从零写第二个 Todoist 界面。Knowledge Bridge 添加“自然语言任务收件箱”“日计划与调整理由”“学习结果”“连接/提醒状态”。

官方 Companion Plugins 文档建议扩展通过运行时 API 读写任务，而非直接重写 frontmatter；应检查 API 版本与能力，并记录变更来源。[S02] 正式集成优先采用该路线。API 方法与字段一律以锁定版本为准，不通过未公开内部对象拼接。

### 4.2 备选及不选理由

| 方案                | 适用                                                       | 当前决策                                                                    |
| ------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------- |
| Obsidian Tasks      | 简单 Markdown checkbox、到期日、循环任务和跨笔记查询 [S06] | 轻量备选；当前需要多元数据、学习关联与计划，优先 TaskNotes                  |
| TaskNotes Workflows | 事件/定时触发的任务自动化 [S05]                            | 不作为自动协调器的必要依赖；避免第二套调度与可执行 Markdown 混入资料库      |
| Todoist             | 现成跨端任务与提醒 [S07]                                   | 可选外部任务主库路线或有限提醒集成；不能同时与 TaskNotes 争同一字段的主写权 |
| 全自研任务 UI       | 特殊交互、无法接受上游契约                                 | 只在 TaskNotes 适配核心门禁失败后替代，不默认重复建设                       |

不要同时让 Tasks、TaskNotes、另一个 recurrence 插件和自研 worker 自动修改同一组任务。

### 4.3 必须核验的兼容性

需要实际测试：自定义稳定 ID/字段保存、TaskNotes 状态映射、事件源标识、重复事件、循环任务实例、计划字段修改、人工并发编辑、打开的任务笔记、暂停插件及重启恢复。

**公开的 update 方法不等于带预期版本的原子更新。** 本轮查到 Runtime API 更新入口，但没有验证其跨插件竞争或强 CAS 保证。[S03] 自动回写 TaskNotes 字段只有在锁定版本通过相应契约/故障测试后开放；未通过时只生成计划投影，不后台修改用户任务字段。不能用“写前读一次”冒充跨所有写入者的事务。

本次不同 TaskNotes HTTP 文档页面的快照包含不同 CORS/bind 描述，不能从缓存页面断言实际安装包已隔离。因此默认关闭它的额外 HTTP/MCP 入口，使用进程内 API 和自己的受认证 Bridge。确需 HTTP 时验证实际监听地址、认证和 Origin 行为，而不只看设置名称。[S04a][S04b]

TaskNotes 仓库另列 Web/iPhone Beta 产品入口；本文只选 Obsidian 插件这条路线，没有核验独立 App 的跨端同步和后台提醒行为，不能将它们视为已解决的能力。[S12]

## 5. 数据在哪里：按域确定事实源，不做三方无条件双向同步

| 数据                             | 事实来源 / 权威提交点                    | 其他副本角色                                              |
| -------------------------------- | ---------------------------------------- | --------------------------------------------------------- |
| 原始来源、固定解析与证据         | 对象仓 + 已提交来源/集合 manifest        | Vault 是可读投影或选择性附件                              |
| 人工笔记                         | 用户 Markdown                            | 索引只读；模型不得整体覆盖                                |
| 正式 Wiki                        | 受控提交的页面版本与 provenance          | 当前 Vault 文件需与提交版本核对                           |
| 用户任务的标题、状态、截止与估计 | TaskNotes 任务文件及其服务行为           | state.db 中是被观察的任务修订投影，不是第二个任意可写主库 |
| 学习尝试、任务关联、批准记录     | 本系统持久学习/操作账本                  | 可导出 Markdown/JSON；不能只靠任务打勾重建                |
| 已接受的时间安排                 | 本系统 PlanRevision/PlanBlock            | `61-Plans` 和日视图是投影；不反向解析显示文本作为授权     |
| 外部会议与忙闲                   | 对应日历服务                             | 本地缓存有时间窗口和 freshness，不能把读取失败当成空闲    |
| 提醒意图                         | 已提交计划/提醒政策生成的 ReminderIntent | 远端 relay 是有版本的执行投影，不任意修改任务             |

建议新增目录，不移动既有人工文件：

```text
60-Tasks/           TaskNotes 实际任务，设置映射到这里
61-Plans/           Bridge 管理的计划投影
62-Learning/        可读学习记录/复习视图
63-Reviews/         每日复盘、变更摘要和冲突报告
90-System/Views/    视图文件与导航
```

日记中嵌入任务链接/视图，而不是把同一任务复制为多份 checkbox。多处展示同一 taskId，状态只有一份。

二进制原件、学习账本、plan/notification 账本、对象与来源清单全部纳入一致备份；索引可重建。只复制 Vault 不能声称已备份完整系统。

### 5.1 写入责任按域分开

Bridge 自动化入口分派：

- 来源/Wiki/计划投影：现有 Writer 的受管路径与冻结补丁。
- TaskNotes 任务：TaskNotes Runtime API adapter；不旁路修改其 frontmatter。
- 人工笔记：默认只读；明确的保存操作另建批准提案。
- 外部日历：可选独立 connector；默认只读，不复用任务写权。

这不意味着能阻止用户、其他插件或同步进程直接改文件。发生第三种内容版本时保留人工内容、重新取证/排期；不给出跨任意本地进程的线性一致性承诺。

## 6. 用户体验：从一条输入到当天可执行计划

### 6.1 统一添加任务

用户可以在 TaskNotes 中添加、在知识页选择“创建学习任务”，或向 Bridge 输入自然语言。三种入口最终都关联稳定 taskId。

自然语言例子：

```text
明天继续学工具调用，预计一小时；先复习之前的错误，再做一个小实验。
```

任务解释器提出：任务标题、目标、估计、日期、依赖候选、需要的资料、完成标准。用户明说的字段和模型猜测分开记录。句子“明天学”默认是计划日期，不自动变成不可延期的硬截止。

缺少时间估计可以给可修改候选；缺少可用时间表时先放 Inbox，返回 `needs_constraints`，不能把工作日全天当作可用空闲。

### 6.2 今日页面

```text
今日计划（Asia/Singapore）

固定承诺 / 可用时间 / 弹性安排 / 缓冲
任务：未开始、进行中、阻塞、已完成
每项：预计、已记录用时、剩余估计、完成标准、下一步
风险：临近截止、缺资料、前置任务未完成、安排冲突
同步：任务快照时间、待写入数、提醒已同步至哪个计划版本
```

“实时反馈”优先输出事实：已完成什么、哪里受阻、是否超出估计、下一步是什么。不要用长篇夸奖替代真正的进度，也不因为没有计时数据就判断用户没做事。

### 6.3 任务开始与完成

开始任务时展示该单元必要资料和上次遗留问题，不把完整知识库塞进模型。完成时允许用户勾选或提交产物；需要实验/回忆评测的学习任务另外记录证据。日常事务可以用户确认完成，不要求每件家务都附文件。

自然语言“做了一半”是用户自报进度，不自动等于通过半数验收项。系统可记录 self_report 并询问剩余量；不由生成模型单方面写成 completed。

## 7. 任务与学习数据模型

### 7.1 必须区分的对象

| 对象            | 核心含义                                            |
| --------------- | --------------------------------------------------- |
| SystemJob       | 系统执行的摄取、索引、编译或研究作业                |
| UserTask        | 用户要做的行动，不等于 job                          |
| TaskOccurrence  | 循环任务的一次实例；完成今天不等于整个系列结束      |
| AcceptanceItem  | 一个可检查的完成条件及权重                          |
| WorkLog         | 某次时间记录；与结果和掌握程度分开                  |
| PlanBlock       | 一个任务实例在日历中的工作时段，可一对多            |
| LearningGoal    | 希望形成的能力或解决的问题                          |
| LearningAttempt | 某个版本范围下的一次回忆、解释、实验或应用记录      |
| ReviewItem      | 需要复习的能力/误区及建议窗口，不按每个段落自动创建 |
| ReminderIntent  | 与任务实例/计划版本绑定的一次通知意图               |

### 7.2 状态正交，避免一条超长状态机

UserTask 生命周期：`inbox / todo / in_progress / blocked / done / cancelled`。是否已排期由 PlanBlock 表示，是否逾期由截止计算，是否需同步由 SyncState 表示，不把三者塞进 status。

TaskNotes 实际状态名称可以配置，adapter 保存双向映射；遇到未知状态显示待映射，不静默转换为 done。任务重复打开不会删除之前的 WorkLog 或 LearningAttempt。

### 7.3 时间字段必须分开

`plannedDate` 是想在哪天做；`notBefore` 是最早允许开始；`deadline` 是必须完成的边界；`scheduled` 是 TaskNotes 中的计划表达；`PlanBlock.start/end` 是本系统已接受安排；`reminderAt` 是通知时刻。

日期型 deadline 和有时刻的 deadline 使用不同类型。日期型截止按指定时区的当天结束边界解释，内部使用次日开始的 exclusive bound；不把“今天截止”变成今天零点已经逾期。

估计使用 `estimateMinutes`、`remainingMinutes`、`estimateOrigin=user|suggested|calibrated`。计时大于预估后继续记真实用时，不自动封顶，也不为了排进空隙把任务时长缩短。

任务依赖是显式 DAG，关联阅读推荐不是硬前置。依赖未知、成环或前置结果缺失时进入解释/阻塞，不悄悄删除边。

### 7.4 循环实例

由 TaskNotes 管理任务循环语义，Bridge 不再另跑一套“每完成一次复制下一任务”的引擎。将原始系列身份、发生时间和时区映射为稳定 occurrenceKey；移动某次排期不改变该次实例身份。[S01]

每日晨间提醒属于通知政策的 recurring intent，不一定需要生成一个占据学习进度分母的用户任务。复习 ReviewItem 与固定每日循环任务也不是同一种重复模型。

### 7.5 案例：任务记录形状

这是本系统的领域对象示例，不是可直接粘贴的 TaskNotes frontmatter：

```json
{
  "taskId": "example-task-01",
  "title": "验证一个工具调用循环并记录停止条件",
  "kind": "learning",
  "status": "todo",
  "timezone": "Asia/Singapore",
  "plannedDate": "2026-09-21",
  "deadline": null,
  "estimateMinutes": 60,
  "remainingMinutes": 60,
  "estimateOrigin": "user",
  "scheduling": { "flexible": true, "splittable": false, "locked": false },
  "dependencyTaskIds": [],
  "learningGoalId": "example-goal-01",
  "sourceSnapshotIds": ["example-source-snapshot-01"],
  "acceptance": [
    { "id": "a1", "text": "解释调用与结果回传的顺序", "weight": 1 },
    { "id": "a2", "text": "完成一次变式实验并记录结果", "weight": 2 }
  ]
}
```

日期、ID 和任务全部是例子，未创建实际待办。

## 8. 插入任务后的自动协调

### 8.1 分工：LLM 理解，程序求解，政策决定能不能应用

```text
自然语言 / 表单输入
 → 结构化任务候选
 → 类型、时间、依赖和权限校验
 → 获取任务与忙闲的固定规划快照
 → 有界确定性排程
 → 返回安排、冲突与调整理由
 → 根据批准 / 受限委托执行
 → 写入回执、更新进度和提醒版本
```

LLM 可以提出工作量、子任务与可解释建议，但不能自己更改截止时间、伪造用户确认、调用无限工具寻找“完美计划”。

### 8.2 硬约束与软偏好

硬约束：固定会议、明确的 deadline、已开始/已锁定任务、前置依赖、可用时段、禁打扰/休息、设备或地点限制、不可拆分时长，以及数据/操作授权。

软偏好：优先级、希望日期、上午/晚上偏好、减少上下文切换、保留缓冲、避免碎片化、减少对已接受计划的改动。

优先级只能在可行范围内排序，不能让“紧急”突破硬约束。日历查询没有覆盖某个日历，不能把那部分时间视为已知空闲。

### 8.3 规划快照

保存 `taskRevisionDigest`、`availabilityRevision`、`calendarFetchedAt`、`calendarCoverage`、`policyVersion`、`now`、`timezone`、`planRevision`。应用前复核；期间出现新会议、用户打勾、截止改变或新任务，旧计划不能无条件提交。

首版接日历只需忙闲，不要求读取会议详细正文。Google Calendar 的 FreeBusy API 提供给定范围的忙闲信息，可用于这一边界。[S08]

### 8.4 可实现的初始算法

1. 选择未来 7 天范围内需要安排的任务实例，初始最多 100 个；这些是有界默认值，不是产品能力承诺。
2. 校验依赖无环；剔除已完成/取消，保留已开始与锁定安排。
3. 由可用时间减去固定承诺、休息、缓冲和锁定工作块，得到可用区间。
4. 按硬截止余量、前置解锁价值、明确优先级、已接受安排的稳定性排序；同分用稳定 taskId 打破平局。
5. 逐个放入连续区间；仅对显式可拆任务按 minChunkMinutes 拆分；依赖任务必须能在前置实际完成或保守可行完成时间后开始。
6. 尽量保留旧计划，仅移动受影响的弹性块；有界回溯，达到搜索预算就停止。
7. 输出冲突、未排任务和选项。每日计划可以部分可行；未排任务不可丢失。
8. 独立校验输出没有重叠、越界、遗漏依赖、突破 deadline 或未经授权的改动。

这是启发式初始排程，不承诺全局最优。区分 `feasible`、`partial`、`no_plan_found`、`infeasible_proven`、`needs_constraints`。只有依赖成环、可用总容量不足等有证明依据的情形，才能标“确定不可行”；一次贪心失败只代表未找到方案。

### 8.5 最小改动原则

已经开工的任务不自动打断；临近开始的安排默认冻结。一次新任务只触发一个去抖后的重排，自己的投影更新不再次触发重排。无实质变化时不新建计划版本、不重新发送提醒。

超额负荷先显示缺口，例如“还需 45 分钟”，然后建议减少范围、延期某项或由用户增加可用时段。系统不能自己压缩睡眠、删休息或修改硬截止。

### 8.6 权限分层

| 动作                          | 默认行为               | 开启受限自动协调后              |
| ----------------------------- | ---------------------- | ------------------------------- |
| 为新任务推导时间/资料候选     | 可以提出               | 可以提出                        |
| 放进空闲且许可的个人时段      | 展示计划，等待采用     | 在明确委托范围内自动应用        |
| 移动当天未开始的弹性块        | 展示差异               | 可在最大位移/次数限制内自动应用 |
| 跨天移动、扩大每日时长        | 需要确认               | 仍需确认，除非另外明确授权      |
| 修改硬截止、固定会议          | 禁止自动执行           | 仍不得凭一般排期委托执行        |
| 标记任务完成或知识已掌握      | 用户操作或明确验证结果 | 不能凭“看起来做了”自动赋值      |
| 扩大模型/通知外发、启用工作流 | 管理设置批准           | 任务安排权不包含此项            |

采用 `AuthorizationDecision` 区分 `user_action / approval / delegated_policy`。策略自动放行不能写成“用户刚刚点击批准”。知识 Wiki 的人工审核政策不因任务自动排期而放宽。

### 8.7 插入任务示例

以下为 2026-09-21 的虚构排期，非读取自用户日历。假设可用窗口 19:00–22:00，任务尚未开始，休息固定。

| 原安排      | 原内容           | 插入一个 20:00 前完成、耗时 45 分钟的新任务后      |
| ----------- | ---------------- | -------------------------------------------------- |
| 19:00–20:00 | SDK 学习 60 分钟 | 19:00–19:45 处理新任务；19:45–20:00 留 15 分钟缓冲 |
| 20:00–20:15 | 固定休息         | 不变                                               |
| 20:15–21:00 | 代码练习 45 分钟 | 20:15–21:15 安排 SDK 学习                          |
| 21:00–21:15 | 缓冲             | 被上述 SDK 学习占用                                |
| 21:15–21:30 | 固定休息         | 不变                                               |
| 21:30–22:00 | 复习 30 分钟     | 不变                                               |

代码练习不能再塞进当天；系统提出移至下一个确认可用的时段，但跨天尚未授权时保持待确认，不自行宣称已安排明天。新任务并没有凭空增加可用时间。展示具体变更与受影响目标，而不是只回复“已优化”。

## 9. 实时同步：在线更新、离线补偿和回写冲突

### 9.1 事件链

```text
TaskNotes 中创建 / 修改 / 完成任务
 → Bridge 记录观察事件与任务快照
 → 本地服务幂等登记最新任务修订
 → 重新计算相关进度与计划候选
 → Today 视图更新
 → 必要时通过受控通道更新计划投影
 → ReminderIntent 升级/取消旧版本
```

TaskNotes Runtime API 支持任务读写与事件等能力；适配应检查版本/能力，使用 source/correlation，避免自己的修改再次自触发。[S02][S03]

事件不是可靠存储。Bridge 需要本地待发送队列、服务端 inbox/outbox、启动清点、重连清点与按 hash 补偿。事件重放后先读取当前任务事实，不能按旧事件到达顺序回滚状态。

### 9.2 目标与限制

本地任务视图应随 TaskNotes 变更更新。Bridge 在线条件下，初始端到端状态反馈目标 p95 < 2 秒、轻量重排目标 p95 < 5 秒；它们是待测目标，不包括 LLM 长文生成与跨设备网络同步。

断网或服务关闭时，用户仍能在 TaskNotes 管任务；Bridge 显示 `pending_sync`。恢复后补事件并核对源文件，不凭空补写不存在的回执。Obsidian 关闭时服务可读最后已确认快照，但应标 `lastSyncedAt`，不称最新。

### 9.3 Plan 与 TaskNotes 日期的关系

首版完整时段安排只在 PlanRevision 中管理，并由 Bridge Today/计划投影展示。TaskNotes 自带的 `scheduled` 可以保留用户原有意图；不要求首版把所有 PlanBlock 同步成一组可编辑日历事件。

需要在 TaskNotes 日历显示安排时，另启用经过测试的 adapter 投影：多段安排不能塞成一个假的起止区间；所有投影标记来源和计划版本。用户手动修改投影时作为新的计划约束请求处理，而不是简单“谁最后写谁赢”。

在 TaskNotes 更新路径尚无可验证的并发保护时，计划继续可计算和展示，但自动修改任务字段保持关闭。该限制不阻止用户自己通过 TaskNotes UI 接受安排。

### 9.4 外部日历

默认只读忙闲。若后续需要创建个人时间块，只允许写独立“KB Plan”日历；不改带参与者的原会议。外部事件保存 ID、版本/etag 与 planBlockId，不通过标题去重。

增量同步失效需区分原因。Google Calendar 对无效 syncToken 要求重新完整同步；只能重建相应日历缓存，不能把自己的任务账本也删掉。[S09] 日历查询失败或过旧时停止自动应用可能冲突的新安排，保留已知承诺和等待核对提示。

### 9.5 远端新增与多设备边界

外部 Agent 或未来远端输入入口在 Obsidian 关闭时，可以持久登记 TaskCapture，但状态是 `awaiting_task_writer`，不能返回“已创建正式任务”。插件重新上线后，复核授权与重复记录，经 TaskNotes adapter 创建任务并取得稳定身份和回执，才能推进为正式 UserTask。提前计算的安排只能标为候选，不发送以其已生效为前提的开始提醒。

移动端人工改动可以通过既有文件同步到主设备；本系统的自动计划应用仍只允许一个权威设备。不要在两台设备同时启用同一套自动排期写入。主设备重连后先清点最新任务与同步冲突，再接受计划；同步造成的同 ID 副本不得任取一份覆盖。

Today 插件视图读取受控状态，可在打开时持续更新；普通 Markdown 计划投影不因为需要“实时”就放弃原 Writer 的人工保护。投影文件正在编辑或发生哈希冲突时，界面继续显示最新计划与“文件投影待更新”，而非强刷整篇笔记。

## 10. 进度反馈：真实记录，而不是虚构一个百分比

### 10.1 四类进度分别显示

| 进度     | 计算依据                                  | 不能代表                  |
| -------- | ----------------------------------------- | ------------------------- |
| 材料收录 | 冻结集合 manifest 中成功/缺失的页面或文件 | 用户学会多少              |
| 任务执行 | 任务实例、完成标准、剩余估计、用户状态    | 知识已经准确              |
| 学习证据 | 回忆、解释、实验和迁移任务的实际表现      | 所有版本/未来时间都已掌握 |
| 知识核验 | 被审核的主张和来源范围                    | 用户已阅读每条主张        |

系统自动生成一篇研究报告，只能让“报告生成”这个 SystemJob 完成；不能自动完成“我理解这个机制”这个 UserTask。

### 10.2 任务进度

有明确验收项时：`progress = 已通过验收项权重 / 当前基线验收项总权重`。没有可检验分解时，用状态和用户自报，不展示精确到个位的“智能推算进度”。

累计用时、预计用时、剩余量分开。计时达到 60/60 分钟不等于完成。新增验收项或扩大任务范围时生成 scopeRevision，分别展示“原计划完成”与“新增范围”，不让系统改变分母却责备用户进度倒退。

项目进度默认不把父任务与子任务重复计数；只统计选定基线的叶子交付项。取消项、延期项和未开始项分别记录，不删除未完成任务来提升完成率。

### 10.3 自动反馈的触发

任务完成、阻塞、明确超时、依赖解锁、硬截止风险、每日复盘时生成反馈；文件每保存一次不发消息。主要数字由代码计算，LLM 只负责可选解释，且要引用任务/日志记录。

学习不足先建议一个具体回忆或变式问题；不因一次错题自动创建几十个任务。复习队列有每日容量和用户可跳过/延后的机制。

## 11. 每日提醒：必须有真实执行者

### 11.1 部署层次

| 部署                                 | 可以做到什么                                       | 不能承诺什么                                             |
| ------------------------------------ | -------------------------------------------------- | -------------------------------------------------------- |
| TaskNotes/Workflows 随 Obsidian 运行 | 应用运行时本地提醒与规则                           | 应用完全退出后独立运行                                   |
| 独立本地服务                         | Obsidian 关闭但服务/电脑仍工作时执行提醒           | 电脑关机或休眠时仍持续在线                               |
| 在线 Reminder Relay + 推送渠道       | 从已同步提醒意图按时发送，电脑关闭也不影响服务运行 | 手机离线/DND一定能立即收到；离线人工修改能立刻被远端知道 |
| 外部任务/日历服务                    | 复用服务商的已登记提醒                             | 自动等同 Obsidian 双向实时事实                           |

TaskNotes 提供相对和绝对提醒数据；它的进程内 API 仅在 Obsidian 运行时可用。[S10][S03] 因而本方案不能把插件中的定时工作流等同于独立在线服务。Workflows 的事件规则可作参考，不是关机提醒保证。[S05]

针对长期每日提醒，推荐独立部署轻量 Reminder Relay，持久保存**最小必要**的 reminderId、taskId/occurrenceKey、计划版本、触发时刻、可公开给该渠道的摘要和取消状态。它不需要收到源码、PDF 原文、学习回答或整个 Vault。

### 11.2 通知渠道

可先接本地系统通知，完成闭环后接一个远端推送渠道。ntfy 支持从脚本通过 HTTP 推送到手机/桌面，适合作为传输组件，但不代替本系统的排期与通知账本。[S11a]

使用 ntfy 时启用认证、按 topic 授权和默认拒绝；随机 topic 名称不是授权控制。官方说明自托管服务默认开放，须显式配置访问控制。[S11b] iOS、Android、网络和系统通知权限分别验收；不把服务接收 HTTP 200 当成用户已看到。

已有 Todoist 工作流可复用其提醒能力；官方区分自动、定时、循环等提醒及平台/套餐条件。[S07] 本文不同时启用 Todoist 和 TaskNotes 为同一任务的两个主库。具体连接器暴露的读写能力也需单独验证，不能以产品有某功能推断当前工具已开放该动作。

### 11.3 建议提醒内容

具体时间尚未由用户确认，下面仅为样例：

| 类型   | 示例                           | 规则                                        |
| ------ | ------------------------------ | ------------------------------------------- |
| 晨间   | 08:45 查看今日三件重点与风险   | 本地时区，每日一次；没有计划也不造任务      |
| 开始前 | 已安排任务开始前 10 分钟       | 已取消/完成不再通知；相对时刻随计划版本变化 |
| 晚间   | 21:30 查看完成、阻塞和明日候选 | 展示实际记录，不虚构用户当天行为            |
| 风险   | 任务可能无法在硬截止前完成     | 去重、有解释，避免每分钟重复提醒            |

提醒文案默认温和、可关闭；提供勿扰时段、暂停今天、稍后提醒和按类型退订。提醒次数不能成为学习表现评分。

### 11.4 持久提醒模型

`ReminderIntent` 状态为 `scheduled / dispatching / accepted / failed / cancelled / suppressed / outcome_unknown`。渠道支持送达/阅读回执时再记录 `delivered/read`，不伪造状态。

逻辑提醒键使用 `taskId + occurrenceKey + reminderRuleId + channel`，计划版本作为其递增 generation；单次投递 attempt 另外记录 operationId。日总结的逻辑键使用 `userId + localDate + digestKind + channel`，政策改版本身不应使同一天重复提醒。计划变化时作废旧 generation；取消网络失败保存待同步，不当作已经取消。已投递后是否因重新排期再提醒，必须由显式 rearm 规则决定，不能靠产生新 UUID 隐式重发。详见第 21 节。

发送前再检查当前可知的任务状态、计划版本、授权、quiet hours 和过期规则。重启补偿采用有上限的 catch-up：过期的“10 分钟后开始”不在三天后全部补发；可以合并成一条遗漏摘要。

网络结果不明时可能已经发出，不承诺端到端 exactly-once。保留相同幂等标识并尽量使用渠道的去重；缺少能力时明确重复风险。

### 11.5 离线状态不能伪装实时

如果电脑离线，远端无法知道尚未同步的 TaskNotes 手动修改。将提醒分两类：

- 用户明确授权的固定提醒：按已登记版本执行，并标明计划同步时间。
- 声称“你还没做”的动态催办：任务状态超过 freshness 阈值则暂停，或改为“按最近同步计划，请核对”；不能把旧缓存当当前状态。

排期通知不应超出计划有效期。新设备恢复旧备份后，先与远端提醒账本对账，再恢复发送，避免取消过的任务复活。

## 12. 学习与任务怎样真正关联

LearningGoal 保存目标能力、软件适用范围、重要误区和完成证据，不保存一个笼统的“读完网站”。LearningUnit 引用固定材料集合及必要前置知识；UserTask 引用该单元。

```text
目标：能解释并验证某个 SDK 的工具执行过程
  → 单元：最小流程、错误处理、停止条件
  → 任务：阅读必要资料 / 回忆解释 / 变式实验
  → 尝试：回答、提示使用、实验结果、剩余问题
  → 复习：根据实际缺口生成少量后续任务
```

用户的学习目标不能反过来篡改来源结论。资料更新时标注受影响的单元和尝试适用范围；不抹掉过去正确完成的历史记录。只有需要了解新版本的目标才进入补学候选。

学习编排不等于“所有内容先闭卷”。陌生内容可以先示例和解释，再逐步减少提示。这里采用的是可检验的学习活动设计，而非宣称一种固定流程对所有技能都最优。

## 13. 安全、预算和运行隔离

### 13.1 权限单独建域

最少区分：`kb.read`、`kb.import`、`kb.propose`、`tasks.capture`、`tasks.update`、`plans.propose`、`plans.apply_personal`、`calendar.read_busy`、`calendar.write_owned`、`notifications.send`、`settings.admin`。

身份来自连接/可信 UI。模型建议的优先级、日期、收件人、taskId 和路径仍需校验。抓取页面里的 checklist 不自动成为用户待办；文档中的 Workflow YAML 不自动启用。

TaskNotes Workflows 将 YAML 定义视为可执行配置。[S05] 因此本系统默认不安装/启用其规则执行层；确需使用时只读取单独受信配置目录，禁止自动导入内容进入该目录。所谓“Markdown 可读”不等于“可以无条件执行”。

### 13.2 批处理不阻塞任务与提醒

运行队列分为 interactive、notification 和 batch。任务打勾、提醒检查、轻量排程不排在整站抓取后。长 PDF/语法解析在 worker/子进程中执行，所有队列共用短事务账本和全局资源上限。

LLM 不可用时，TaskNotes、手工任务编辑、现有计划查看和确定性统计继续可用。自然语言输入可回退为表单；不能因模型账单用完就无法勾选任务。

### 13.3 新的隐私投影

任务标题本身可能含公司、医疗或家庭信息。通知渠道拥有的是单独批准的摘要等级，不因为用户允许某云模型就自动允许通知服务获取同一内容。

日历优先只取忙闲；push 默认不含原文、附件和敏感项目名称。日志默认存 ID、时间、hash、状态和计量。外发失败不会自动切换到更宽松服务。

## 14. TypeScript 模块与接口边界

维持原四个工作区，新增服务内模块，不预先拆微服务。Reminder Relay 仅在需要独立在线部署时单独打包。

```text
apps/service/src/modules/
  ingestion/             多类型收录与集合覆盖
  knowledge/             主张、范围、引用与检索
  research/              子问题和证据包
  learning/              目标、尝试、复习
  tasks/                 稳定身份、观察投影、完成标准
  planning/              可用时间、约束、求解、提案
  notifications/         意图、投影、发送与取消
  integrations/          TaskNotes映射、日历、可选提醒渠道
  runtime/               队列、预算、事务、inbox/outbox

apps/obsidian-plugin/src/
  tasknotes-adapter.ts    唯一 TaskNotes 集成入口
  task-event-journal.ts   离线观察和补偿
  today-view.ts          今日安排、风险、同步状态
  plan-review-view.ts    原/新安排差异、批准、冲突
  learning-view.ts       学习证据而非页面计数
```

### 14.1 本系统拟定义的 HTTP 接口

| 接口                                 | 目的                             | 写入边界                                               |
| ------------------------------------ | -------------------------------- | ------------------------------------------------------ |
| `POST /v2/task-captures`             | 从自然语言/表单提出或登记任务    | 用户明确输入后产生受限创建请求；没有任意路径           |
| `POST /v2/task-observations`         | Bridge 上传最新事实快照/变更     | 验证连接、taskId、来源序列与幂等；不是模型自报完成入口 |
| `POST /v2/plan-proposals`            | 根据快照计算安排                 | 只提出                                                 |
| `GET /v2/plan-proposals/:id`         | 查看差异、风险和未排任务         | 只读                                                   |
| `POST /v2/plan-proposals/:id/accept` | 接受固定摘要的计划               | 可信批准或受限策略决定，重新检查基线                   |
| `GET /v2/today`                      | 今日任务/时间块/风险/进度        | 返回 lastSyncedAt 与 snapshot IDs                      |
| `POST /v2/learning-attempts`         | 记录实际尝试/结果                | 受限学习记录，不改源事实                               |
| `POST /v2/notification-policies`     | 配置时区、渠道、时间、隐私和勿扰 | 管理权限；初始关闭                                     |
| `GET /v2/sync-health`                | 任务、计划、通知各自同步情况     | 不回显 token                                           |

这些不是 TaskNotes 官方接口。API version 路由只是本设计；开发时与原 `/v1` 兼容或显式迁移，不静默改变请求含义。

### 14.2 数据表最低要求

在现有 state.db 中新增 `task_commands`、`task_observations`、`task_identity_map`、`task_links`、`task_acceptance_results`、`learning_goals`、`learning_attempts`、`review_items`、`plan_revisions`、`plan_blocks`、`plan_authorizations`、`reminder_intents`、`notification_deliveries`、`projection_receipts`、`connector_checkpoints`。

TaskNotes 自身已有的 timeEntries 与 recurrence 不无条件复制为另一份可写业务状态；本系统存观察版本和引用。独立新增日志必须明确来源和所有者。

唯一约束至少覆盖稳定 taskId、operationKey、实例完成身份、入站事件、通知幂等键。计划块之间不重叠需要应用验证与测试，不能假设一个普通主键就能保证时间区间互斥。

## 15. 落地路线与交付门禁

旧的小时估算只针对旧范围，不能直接覆盖多来源、研究、学习任务和独立提醒。先用里程碑交付并实测，再给扩大范围后的工时，不承诺本文产物已可运行。

| 阶段              | 最小交付                                         | 通过条件                                                      |
| ----------------- | ------------------------------------------------ | ------------------------------------------------------------- |
| M0 统一规范       | 固定 v2 合同、状态、写入域、政策与测试清单       | 不再存在“PDF 在首版/不在首版”的互斥验收                       |
| M1 任务表可用     | Pilot Vault 安装并核验 TaskNotes；任务与资料链接 | 新增、完成、重开、过滤和时间记录可用；未知字段不丢失          |
| M2 在线同步       | Bridge 观察、任务投影、Today、离线补偿           | 断线改任务重连一致；自回声不导致循环                          |
| M3 建议式排期     | 可用时间、忙闲、依赖、插入任务、差异预览         | 无重叠/越界，冲突可解释；不改硬截止和会议                     |
| M4 进度与本地提醒 | 独立进度、有限学习任务、本地通知                 | 计时不冒充完成；应用关闭边界清楚；可暂停                      |
| M5 在线提醒       | Reminder Relay/已选渠道、取消、恢复与 freshness  | 电脑关闭测试、状态过期、重复/丢回执、旧备份恢复全部有正确处理 |
| M6 受限自动协调   | 策略委托、计划回执、异常回退                     | 并发/多端/插件契约门禁通过后，仅对明确范围启用                |

知识摄取和研究模块可以与任务表并行迭代；不要等所有 PDF 增强完成才能使用 Todo。反过来，Todo 可用也不意味着资料摄取和知识准确性已经通过验收。

### 15.1 首批任务建议

以下是开发工作包，不是已经添加到用户待办的真实任务：

| 工作包                    | 主要产物                                          | 核心断言                                                        |
| ------------------------- | ------------------------------------------------- | --------------------------------------------------------------- |
| W01 TaskNotes 契约试点    | adapter-contract 测试、字段/版本映射              | 保留自定义 ID、未知字段、正文；重复事件幂等；不依赖内部 API     |
| W02 稳定身份与观察        | identity-map、event-journal、reconcile            | 改名 ID 不变；复制同 ID 报冲突；删除不复活                      |
| W03 计划模型              | tasks/availability/plan schemas                   | 日期与时刻不同；依赖成环拒绝；缺可用时间不猜空闲                |
| W04 有界求解器            | solver、validator、explanations                   | 固定块不变；不强行塞满；未找到不冒称不可行                      |
| W05 提案与写入域          | review UI、domain writer registry                 | 截止变化使提案失效；TaskNotes 自写不走裸 fs                     |
| W06 学习与进度            | attempt/result/baseline 模块                      | 看过页面≠掌握；用时≠完成；新增范围另列                          |
| W07 通知意图              | timezone/recurrence/intent ledger                 | 当地日期正确；改期取消旧通知；错过通知有限补偿                  |
| W08 在线提醒与恢复        | relay、minimal payload、cancel/ack                | 电脑关机仍能发送已登记提醒；陈旧状态不催促未完成                |
| W09 安全与升级门禁        | egress、snapshot、fault suite                     | 恶意文档不能创建任务/启用 Workflow；旧 backup 不重发已取消通知  |
| W10 状态命令与去重        | task-commands、operation receipts                 | 重复完成不反转；一个变更的多个事件只推进一个事实修订            |
| W11 计划提交与投影        | plan-CAS、projection receipts、calendar ownership | 两份旧计划仅一份可提交；文件/日历失败独立显示；不吞原来会议     |
| W12 提醒 authority 与代际 | logical reminder key、relay generation、handover  | 旧投递不能覆盖取消；本地/远端不同时发送；政策变更不重发当日摘要 |

每项采用先写失败用例、实现、回归、独立审查的顺序。只有真实 TaskNotes/Obsidian 集成测试能证明该组合有效；内存模型和纯函数单测不能替代插件行为验证。

| 同步   | 部分文件写入后崩溃                            | 恢复或明确冲突，不静默部分成功                       |
| 学习   | 抓取100页、模型生成报告                       | 不增加个人掌握进度                                   |
| 学习   | 计时60分钟但任务未达标准                      | 显示用时和剩余任务，不能自动done                     |
| 学习   | 学习范围新增                                  | 单独报告 scope change，不伪装退步                    |
| 提醒   | Obsidian关闭但本地服务运行                    | 按部署支持范围处理；不依赖插件任务继续跑             |
| 提醒   | 电脑关机                                      | 在线relay只用已确认提醒；无relay则明确不可用         |
| 提醒   | 远端同步落后、用户可能已完成                  | 不发送“你肯定没做”的断言                             |
| 提醒   | 发出后响应丢失                                | unknown/去重处理，不声称零重复                       |
| 提醒   | 改期、取消、跨时区                            | 旧intent取消，新计划对应时刻正确                     |
| 提醒   | 恢复旧备份                                    | 先对账远端，已取消通知不复活                         |
| 隐私   | 任务标题含敏感项目                            | 渠道摘要按独立授权脱敏                               |
| 注入   | 抓取页含任务/Workflow指令                     | 当资料保存，不执行/不自动成为用户意图                |
| 可用性 | 模型失败、批量PDF正在解析                     | 任务勾选/Today/基本提醒不被阻塞                      |
| 权限   | MCP模型调用approve或改会议                    | 被拒绝，且没有外部副作用                             |
| 去重   | 同次完成收到 updated/status.changed/completed | 单个事实修订，进度不重复累计                         |
| 重试   | 循环实例完成成功但回执丢失                    | 先核对目标状态，不再次执行 toggle 反转               |
| 计划   | 两份建议依据相同旧 planRevision 同时接受      | CAS 只提交一个，另一份重新规划                       |
| 投影   | 计划已接受但 Markdown 正在编辑                | Today 显示最新计划，文件标 pending，不强刷正文       |
| 日历   | 自有 KB Plan 日历包含投影块                   | 不作为外部忙闲再次扣容量                             |
| 提醒   | 旧 generation 到达晚于取消                    | 拒绝旧代际，不复活提醒                               |
| 提醒   | 同一天只调整通知政策版本                      | 不再次发已发晨间摘要                                 |
| 提醒   | 本地与远端同时认为自己负责                    | authority 核对失败的一方停止；未知在途结果先对账     |

测试通过率、延迟和实际费用需标明硬件、版本、语料与样本数量。此表是目标，不是本次跑分。

## 17. 示例政策与首次启用

具体工作时段、可用学习时长、提醒时间/渠道尚未由用户确认。不要从历史某个学习计划自动继承为当前日程。

下面配置可被本项目未来的 schema 解释，不能直接导入 TaskNotes：

```json
{
  "schemaVersion": 2,
  "timezone": "Asia/Singapore",
  "taskAdapter": "tasknotes-runtime",
  "planning": {
    "mode": "propose_only",
    "horizonDays": 7,
    "maxTasks": 100,
    "maxSearchNodes": 2000,
    "freezeBeforeStartMinutes": 30,
    "allowCrossDayAutoMove": false,
    "allowHardDeadlineChange": false,
    "allowMeetingWrites": false,
    "requireFreshConfiguredCalendarsForAutoApply": true
  },
  "notifications": {
    "enabled": false,
    "remoteRelayEnabled": false,
    "channels": [],
    "includeSensitiveTitles": false,
    "suppressDynamicNagWhenStale": true
  },
  "learning": {
    "createTasksForEveryImportedPage": false,
    "autoMarkMastered": false,
    "reviewSuggestionsRequireCapacity": true
  }
}
```

首次启用顺序：复制 Pilot → 备份 → 从 Obsidian 社区插件中核对维护者并安装 TaskNotes → 设置任务目录及状态映射 → 手工创建/完成/重开三项任务 → 打通只读观察 → 展示建议式计划 → 配置真实可用时间 → 测试本地提醒 → 需要关机提醒时再部署独立在线渠道 → 最后验证并开启受限自动协调。

本次不执行任何安装或实际任务写入。不能因为文档里有示例时间就创建日历事件，也不能因为用户说“希望自动协调”就默认授予所有会议和截止日期修改权。

## 19. 任务命令、重复事件和不确定重试

### 19.1 不把 toggle 作为可随意重试的远端命令

本轮 Runtime API 文档包含 `recurring.toggleCompleteInstance`；同一次状态修改还可能产生 `task.updated`、`task.status.changed` 和 `task.completed`。[S03] 这些是接口可见行为，不能将每条事件都当成一次新的任务完成。

本系统的命令应表达目标状态，例如“实例 X 应为 completed”，而不是“把实例 X 的状态反转一次”。建议记录：

```text
operationId
actorId / trustedAuthorization
stableTaskId + occurrenceKey
expectedObservedRevision
intent = set_completion
desiredCompleted = true
state = accepted / executing / confirmed / rejected / outcome_unknown
```

这不是 TaskNotes 已提供的 CAS API。adapter 先检查锁定版本是否有目标状态接口；若只能调用 toggle，则先在受控串行通道核对当前状态，只在确实需要改变时调用一次。超时或插件断连后进入 `outcome_unknown`，重新读取事实并比对，绝不能直接重发 toggle。无法排除用户随后又手动切换的情况时，暂停并展示冲突，不能把“与目标一致”当作该次操作已经成功的审计证明。

直接由人通过 TaskNotes UI 操作的完成不需要再弹一轮 Wiki 审批。把它记录为 `user_action`；不要为了所有写入统一而让每次打勾都生成复杂审核单。模型提议的完成、批量改截止和跨域操作不享受这项便利。

### 19.2 事件处理按事实修订收敛

收到事件后读取当前任务，生成业务字段 digest；同一 digest 不再重复推进任务修订。事件记录仍可保留供审计。`source/correlationId` 用于跟踪，不是可靠唯一事务 ID，更不能作为授权主体。

`events → 持久 inbox → 最新事实读取 → task revision → progress/plan invalidation`；服务重启后先从源文件重新清点。离线期间记录的旧事件只是“需要核对”的线索，不应覆盖较新的 TaskNotes 状态。

任务路径是当前位置，不是业务身份。优先用通过契约测试的自定义稳定 ID 字段；改变标题或路径不换 ID。复制出两个相同 ID 时进入冲突队列，不能默默随机改一个后继续排程。外部创建命令超时后按本地操作映射、固定 ID 和实际文件共同核对，不以标题去重。

## 20. 计划接受、文件同步与日历投影的提交边界

### 20.1 计划不是任务截止日期的副本

任务意图与具体排期分开：TaskNotes 保留任务状态、due、scheduled 意图和 timeEntries；服务里的 PlanRevision 保存已接受的工作时段。一个任务可以跨多个工作块，不能把一段时间塞进 due 字段，造成“改期其实改了截止”。

第一版只在 Bridge Today 视图显示精确排期，不后台改 TaskNotes 的 scheduled。这就允许先交付自动计算和低风险计划采用，不被上游写入 CAS 能力阻塞。

### 20.2 计划接受使用本系统账本的并发检查

```text
准备：读取权威插件当前任务集 + availability + 日历覆盖 + policy
计算：产出 plan proposal / basePlanRevision / inputDigest
接受：服务短事务核对已知基线仍匹配 → 新 PlanRevision + outbox
投影：Today / Markdown / 可选日历 / 通知分别消费 outbox
回执：各投影记录目标 revision、状态、错误与校验结果
```

PlanRevision 的接受是 state.db 中的明确提交点，不要求可读 Markdown 已经写完。这个新规则只针对计划领域，不改变原始来源与正式 Wiki 的既有受控提交规则。投影未完成时 UI 显示 `plan accepted / vault projection pending`，不能声称所有地方都已同步。

由于 TaskNotes 和外部日历不是该 SQLite 事务的参与者，不能声称这个事务锁住了全世界的任务或会议。插件在线时进行一次新鲜读取，观察到后续改动即让受影响计划失效；有未确定在途写入或同步冲突时，停止自动采用。日历新会议也可能在接受后到来，系统应告警并重排，而不是对未来冲突作绝对保证。

每个已接受计划基于 `basePlanRevision` 做比较更新，防止两份候选并发覆盖。外部日历投影失败不会回滚已发生的用户行动，也不能把已记录的完成变回未完成。

### 20.3 不让计划日历制造自我冲突

需要外部时间块时，使用单独“KB Plan”日历，初始只读取其他选定日历的忙闲。否则自己的计划块再次作为忙闲输入，就会重复扣减可用时间。

FreeBusy 返回时间区间和各日历的错误状态，不提供逐事件身份。[S08] 不能只看一段区间就猜它属于自家事件并删掉。若必须混合日历，应使用可核对 eventId/owner 的事件读取方案，且不得消除同一时段真正存在的第三方会议。

默认不启用 TaskNotes 自带双向日历写入与 Bridge 的日历投影同时管理相同任务。选择一个投影 authority；不因为两个插件都支持日历就全打开。

### 20.4 自动应用规则应可检查、可撤销

初始策略是 `propose_only`。可信用户可以开 `within_day_flexible`，只允许安排已获委托范围内的当日个人弹性块；保留已开始、锁定和即将开始的安排，不改 deadline、不跨天、不改会议、不扩可用时间。撤销计划不代表能撤销已经开始的工作或已发出的通知，应产生新的计划修订和取消意图。

实际工作/学习时段尚未确认，因此交付配置中的 availability 为空；系统要返回 `needs_constraints`，不是沿用几个月前的 2 小时学习计划。没有接日历时可以依据明确输入的本地时间窗口给出“未核对外部日历”的候选；配置了日历但查询失败，则是未知，不是空闲。

## 21. 提醒的逻辑身份、发送者和离线事实

### 21.1 一个逻辑提醒只有一个执行者

按用户/任务实例/提醒规则/渠道建立逻辑 key，记录：executor、generation、scheduledAt、validUntil、lastTaskObservedAt、cancellationGeneration。选择本地服务或远端 relay 作为该 key 的 authority，不能让 TaskNotes 本地提醒、Bridge 和 relay 同时发同一条开始提醒。

执行端切换先冻结该逻辑 key，核对旧端是否有在途投递，停用旧 authority 后再启用新端。租约过期只能停止新的服务授权请求，不能撤销已在网络上传输的消息；未知投递需对账或报告，不承诺完全零重复。

### 21.2 generation 与发送幂等分开

较新的 generation 覆盖旧排期；乱序到达的旧消息不能取消新提醒、覆盖取消墓碑或复活任务。取消只完成本地提交时，应显示 `cancel_pending_remote`。HTTP 返回成功只表示对应端接受，不等于手机收到或用户看过。

一天的晨间摘要默认只发一次。修改文案、计划或政策不自动触发第二次；想再次推送需明确 reissue 规则。循环任务的 occurrenceKey 不随移动排期改变，否则一次任务挪三次会被当成三次重复实例。

恢复备份时先比对 relay 的代际与已发送记录，不把旧本地数据直接覆盖远端。若做了数据清除，取消墓碑也属于必须核对的状态，不随索引重建消失。

### 21.3 固定提醒与动态进度提醒分别设计

“每天提醒我检查计划”可以预先登记为不依赖即时状态的固定提醒。它在本机离线时仍可发送，但不能附带未经更新的确定性进度结论。

“你还有两项没做”需要较新的任务观察。状态超过配置的 freshness 阈值时，退化为“按上次同步计划，请核对”或暂不发送。时间戳属于内容的一部分，不只是日志里的调试信息。

电脑离线后，relay 只能执行已经登记的规则和已同步摘要。手机离线、通知权限、勿扰、推送服务故障都可能影响到达，应通过目标设备验收；它不是紧急或生命安全提醒系统。

### 21.4 本地优先与真正跨端实时不是同一产品承诺

本方案的默认模式为 Obsidian/TaskNotes 任务事实、本地服务排程、可选远端提醒投影。电脑关闭时远端新输入先成为待处理 capture，无法假装正式 TaskNotes 文件已经创建或最新状态已经同步。

若以后要求“电脑永远不开也能在手机新增/完成/自动重排，Obsidian 只是同步副本”，需要改为一个在线任务权威库（例如现有 Todoist 路线或专门服务），再把 Obsidian 作为投影与编辑命令入口。那是 authority 迁移，而不只是添加一个通知接口；不能同时承诺无在线权威服务、任意设备离线写入及全局即时一致。

当前可用的 Todoist 连接器暴露了提醒查找、创建、更新和删除函数，表示未来有接入操作路径；本次仅查看函数定义，没有验证当前账号权限、套餐、发送效果或 Obsidian 同步。

## 22. 一套可以先用起来的实施与验收安排

### 22.1 第一批就做五件事情

| 顺序 | 实际产物                              | 验收方式                                              |
| ---- | ------------------------------------- | ----------------------------------------------------- |
| 1    | 统一 v2.1 规范及旧条款替换表          | 多格式输入、数据所有权、在线/离线边界不再互相矛盾     |
| 2    | Pilot 内 TaskNotes + 三个手工样本任务 | 创建、修改、完成、重开、改名后任务与链接不丢          |
| 3    | Bridge 只读观察 + Today 面板          | 同一次完成多个事件不多计；服务重启不回滚状态          |
| 4    | 可用时间设置 + 建议式排程             | 插入新任务返回差异、未排项和原因，不越硬约束          |
| 5    | 确定一个提醒执行端并真实测试          | 改期、完成、取消、关应用/关机、恢复后行为符合选定部署 |

随后才启用自动采用计划、复杂日历双向编辑及额外任务应用。多来源摄取/研究和个人任务可分别交付，但它们都通过同一身份、权限和对象/账本基础设施，不另外搭一套宽权限 Agent。

### 22.2 最少用户设置

实际启用排程/提醒时需在界面填写：时区（本方案默认 Asia/Singapore）、明确可用窗口、固定承诺的来源、任务估计/可拆分规则、允许自动移动范围、通知渠道、晨/晚提醒时间和勿扰策略。当前文档不替用户发明这些值，不据此创建实际日程。

只希望先用任务表时，这些配置不是创建和勾选任务的前置条件；任务可以先留在 Inbox，不强迫每项都有截止时间、学习目标和提醒。

### 22.3 不沿用旧工时，也不把文档检查当上线

原 E00–E14 与 96–150 小时针对旧个人 V1。新增多源采集、研究、TaskNotes 集成、排程、跨端提醒后，需要分别估算/跟踪 W01–W12 和知识域任务。本轮不提供没有运行和兼容性依据的整体完成日期。

TaskNotes 安装、Runtime API 兼容、插件 UI、真实源资料、手机通知和文件恢复均需要实际测试。本文的字段与断言支持后续编码，但没有交付可运行的插件或服务。
