# 基于 Obsidian 的知识库：落地实施手册

**版本：1.0｜日期：2026-09-20｜对象：知识库使用者、TypeScript 实现者、验收者**

> 先建立一个每天能用的小型知识库，再补齐自动化。本文把“现在就能做的人工步骤”“需要开发的能力”“开发后才能执行的命令”分开。随包没有已经编译的服务或插件，不能把方案包当成一键安装软件。

## 1. 你应该走的唯一主线

**新建试点 Vault → 放入一小批真实资料 → 固定问题集 → 开发可追溯的词法资料库 → 接入知识编译提案 → 人工审核后写入 → 演练恢复 → 转为日常使用。**

不先安装 PandaWiki、不先租服务器、不先采购向量数据库，也不先把全部历史资料导入。上轮研究中的项目是实现参考，不是你必须安装的全家桶。

### 1.1 谁负责什么

| 角色 | 负责 | 不应代办的事项 |
|---|---|---|
| 你：知识拥有者 | 选资料、定义真实问题、确认隐私、检查重要结论、批准写入 | 不需要替系统手工修数据库 |
| TypeScript 实现者/编码 Agent | 按任务实现、测试、记录依赖版本和缺陷 | 不替你批准知识、开放外发或跳过门禁 |
| 验收者（可以是你） | 按固定案例测试、查引用、做恢复演练 | 不能只看演示视频或单次正确回答 |

如果由你一个人完成，仍分开这三个动作：写代码后，换到验收清单逐项检查；不要把“我觉得实现了”当成验收通过。

### 1.2 四个交付阶段

| 阶段 | 用户能做什么 | 放行条件 |
|---|---|---|
| M0 人工 Pilot | 剪藏、阅读、链接、记录问题 | 来源边界清楚，资料有用 |
| M1 可追溯资料库 | 导入固定来源、离线关键词检索、打开原文 | E01–E07 通过，不要求接模型 |
| M2 可审核 AI Wiki | 提案、diff、来源问答、批准后写入 | E08–E11 通过 |
| M3 正式个人使用 | 有备份、恢复、撤回、预算和回归评测 | E12–E14 通过，才能开放真实写入 |

MCP、向量、复杂 PDF 和发布分别进入 E15–E17。恢复是 M3 的前提，不是“有空再加”的增强项。

## 2. 现在能做：创建人工试点 Vault

### 2.1 打开随包模板

解压 `Obsidian-KB-Implementation-Package-2026-09-20.zip` 后，找到 `starter-vault`。在 Obsidian 选择 **Open folder as vault / 打开文件夹作为仓库**，选择这一目录即可；Vault 本质上是本地文件夹，官方支持这一入口。[S01]

更推荐先复制模板到自己的长期目录。以下命令只创建新的试点目录，不修改原 Vault；从解压后的方案包根目录执行。示例适用于 macOS/Linux 终端：

```bash
# [现在可执行：纯文件复制，不安装软件，不调用模型]
mkdir -p "$HOME/Knowledge"
if [ -e "$HOME/Knowledge/Knowledge-Pilot" ]; then
  printf '%s\n' '目标已存在，请换一个新的试点目录；本步骤不覆盖它。'
else
  cp -R ./starter-vault "$HOME/Knowledge/Knowledge-Pilot"
fi
```

随后在 Obsidian 打开 `Knowledge-Pilot`，从 `90-System/首页.md` 开始。模板没有自动 AI 能力，不含插件、密钥或后台任务。

### 2.2 初始设置

先使用核心功能：文件浏览、Search、Backlinks、Properties、Templates。Templates 目录指向 `90-System/Templates`。不要求安装 Dataview、Local REST API 或多个自动改写插件。

试点先不启用跨设备同步，尤其不要把运行数据库放到同步盘。整个 Vault 做一次本地副本后，再加入实际资料。模板中的规则是本项目建议，不是系统安全策略；之后真正的安全配置在 Vault 外。

### 2.3 官方 Web Clipper 配置

从 Obsidian 官方入口或官方仓库指向的浏览器扩展安装，不下载名称近似但来源不明的扩展。[S02]

在 Clipper 的模板设置中配置：目标 Vault=`Knowledge-Pilot`，保存目录=`00-Inbox`，行为选择创建新笔记。标题使用文章标题并避免同名覆盖；建议保存时间或唯一后缀。正文用正文提取变量，来源 URL、标题、作者、发布日期按网页实际可获得信息写入 properties。变量与模板入口以当前官方说明为准。[S03][S04]

本方案不强塞一个未经你浏览器实测的 Clipper JSON 模板；按上述字段手动设置一次即可。避免把 URL/标题直接拼入未转义的 YAML。没有发布日期就留空，不把剪藏日期当发布日期。

**第一次剪藏检查：** 与原网页对照标题、正文起止、代码块、表格和引用。登录墙、X 长文、折叠段落可能只保存部分内容。无法确认完整时标记 `coverage: unknown`，不要写成 full_text。

## 3. 先准备 30 份资料，不导入整个资料仓库

### 3.1 第一批资料建议

这是一组适合技术知识库的样本配额，不要求你先准备几百篇文章。

| 类型 | 数量 | 为什么需要 |
|---|---:|---|
| 与当前工作直接相关的官方 Markdown/网页 | 10 | 有明确问题，能验证准确性 |
| 针对同一主题的设计分析/教程 | 6 | 测试综合理解和来源观点区分 |
| 旧版/新版成对文档 | 4 | 测试版本变化，不能只会追加 |
| 自己的项目笔记/决策草稿 | 4 | 测试“我的判断”与“外部事实”区分 |
| 异常样本 | 6 | 重复来源、两字词、代码符号、截断、私密、注入文本 |
| 合计 | 30 | 一半用于快速迭代，另一半保留验收 |

你可以围绕 Agent/MCP、一个 SDK 的文档审核或一个具体项目开始；不要把健身、旅行、财务与所有技术主题一次混入。第一阶段越聚焦，越容易判断知识库是否真的有用。

### 3.2 逐份登记

使用 `templates/来源登记表.md`。至少写：标题、来源地址/文件、所属主题、捕获时间、文档版本、是否完整、为什么值得保存、是否允许发到指定模型。

**不入库：** 未选择的全量聊天记录、纯广告页、只有链接没有正文的占位、已经过期但没有版本说明的教程、没有复用价值的临时输出。可以保留在 Inbox，但不急着编译。

V1 的自动导入不支持 PDF、Office 和 ZIP。重要 PDF 可以先留在人工附件区；正文由人整理成 Markdown 时必须注明“人工摘录”，不冒充完整 PDF 解析。V1.1 再加入解析流水线。

### 3.3 建立 20 个真实问题

在 `40-Projects/知识库试点.md` 登记问题；不是让 AI 自己出题再自己判分。

| 类别 | 数量 | 示例提问方式 |
|---|---:|---|
| 直接定位 | 6 | “文档哪里说明这个配置的默认值？” |
| 中文别名/代码符号 | 4 | “权限、重排、某个完整函数名能找到吗？” |
| 多来源综合 | 4 | “这两套方案在同一约束下有什么差异？” |
| 版本与时效 | 3 | “旧版结论在新版还成立吗？” |
| 资料中没有答案 | 3 | “文档未给出的性能数字是什么？” |

为每题先标注正确来源和必要条件。没有答案的题应得到“证据不足”，不能奖励猜得像真的回答。随包的 synthetic fixtures 是工程样例，不能替代这 20 道真实题。

### 3.4 M0 完成条件

你能在原生 Obsidian 中找到 30 份资料；每份有来源/覆盖说明；20 个问题至少能人工判断答案或不足；现有人工笔记没有被任何自动插件改写。达不到这一点，先改选材，不继续堆 AI 功能。

## 4. 开发前确定项目边界

### 4.1 仓库只有四个初始工作区

```text
apps/service           本地服务、领域模块、SQLite、模型调用
apps/obsidian-plugin   交互、来源上传、受控 Writer
apps/cli               初始化、配对、诊断、备份维护
packages/contracts    共享类型与运行时 schema
```

依据《01-技术方案》创建代码仓库；不要把整个 Vault 放进服务源码仓库。资料目录、运行目录、源码目录三者分开。

### 4.2 依赖锁定步骤

采用 Node 24 作为服务主版本是本轮设计选择，实施时从官方支持的 24.x 中选择一个实际受测补丁；上游编译包也要求 Node >=24。[S05][S06]

记录以下内容到 `docs/decisions/dependency-baseline.md`：操作系统与架构、Obsidian 应用/安装器版本、Node/pnpm 精确版本、lockfile hash、编译器包版本和 integrity、对应仓库 commit、启用的模型路线。

不要将 `main`、`latest` 或 README 的版本号直接作为发布记录。先检查实际包可下载、导出存在和 native 依赖能安装，再提交 frozen lockfile。

### 4.3 编译器只做一次限额明确的技术验证

执行 E00：在独立工作区验证 `ingestText`、review compile、候选读取、出处映射、用量获取和故障行为。正式 Vault 不作为 SDK root。

| 结果 | 决策 |
|---|---|
| 全部关键门禁通过 | 实现 atomic adapter |
| 能生成页，但不能可靠映射引用/限制内部调用 | 不进正式路径；用 native adapter |
| 只缺少一个边界清晰的适配钩子 | 可做小补丁并记录维护成本，仍需完整门禁 |
| 依赖或模型账号暂时不可用 | 继续做无模型资料库，不让 E01–E07 停工 |

上游 current search 需要模型凭据，不能直接当作本系统离线搜索；query save 的审核边界也不同，因此不启用它。[S07][S08]

GD4AI 不作为依赖前提。要比较体验，只在另一个空 Vault 中使用，不允许它和本系统同时改写正式 Wiki。

## 5. 开发任务与工作量

详细任务见《03-开发任务与验收》。下面是规划估算，假设一名熟悉 TypeScript 的工程师，测试数据和模型账号可用；不包含采购、正式 SDK 安全审计或复杂 PDF 功能，也不是对完成日期的承诺。

| 批次 | 任务 | 预计工程工作量 | 可展示产物 |
|---|---|---:|---|
| A 基线与保护 | E00–E03 | 20–30 小时 | 复用决策、合同、SQLite、身份/政策 |
| B 来源闭环 | E04–E07 | 28–44 小时 | 插件连接、受控来源导入、离线检索 |
| C AI 闭环 | E08–E11 | 28–44 小时 | 预算、编译提案、问答、完整审核 UI |
| D 正式使用门禁 | E12–E14 | 20–32 小时 | 备份、撤回、恢复测试、试点发布 |
| 合计 | E00–E14 | **96–150 小时** | 正式个人 V1 |

上游不能复用时，native adapter 可能增加 8–16 小时；真实数据复杂度或兼容问题可增加额外工作。不要把这些工程工作量机械换算成“某天必定交付”。兼职实施以任务完成和门禁为节奏，不按日历硬上线。

### 5.1 每批必须给你的演示

A：故意用只读身份批准提案，看到 403；用不同内容复用幂等键，看到 409。

B：关闭所有模型配置，导入一篇 Markdown，搜索“权限”和代码符号，点击回到固定原文；重复导入无重复副作用。

C：对一篇资料生成提案，手改目标文件后尝试应用，必须出现冲突；换成有效基线后审核成功，问题回答附有效引用。

D：写到一半杀进程、从备份恢复、撤回来源后查询旧 snapshot，结果必须符合恢复/撤回规则。

## 6. M1：先让来源库可用

### 6.1 实现顺序

E01 合同/工程 → E02 持久账本与对象库 → E03 身份/政策 → E04 bridge → E05 Writer → E06 来源导入 → E07 无模型检索。

不要先实现聊天界面。第一项可见价值是：**同一文件的来源和版本能保存，检索能找到准确段落。**

### 6.2 你应执行的验收

取一篇中文 Markdown；保留原文副本；从插件选择“导入选中资料”，确认 source-only 写入清单；查看 `10-Sources` 下的版本与 parse；进行搜索并核对原文。

重复同一导入；修改原文一个有意义的值，并选择“更新已有来源”再次导入。应有两份不同修订，而不是旧文件被替换。旧问题引用仍能定位旧版。

不给模型密钥时，搜索能运行；AI 提问按钮应说明“模型未配置”，而不是请求失败后输出编造答案。

### 6.3 M1 放行条件

30 份资料中受支持输入均可导入或得到明确的质量警告；“权限”“重排”和完整代码符号可查；全部引用固定版本；人工区 hash 不变；插件断连不会触发服务绕过写入；同一来源重复导入无重复已提交副作用。

## 7. M2：开启模型，但先不要开放自动改写

### 7.1 先配置一个模型路线

在可信管理入口登记 provider、modelId、baseURL、密钥引用、token 限额、单价和外发范围。尽量先只用一个路线，减少排查变量；用户实际选择的模型与价格是运行配置，不在本文杜撰。

使用一份无敏感信息的 synthetic 文档做握手测试：结构化输出可解析、用量能记录、预算预占正确。此时 `writes.allowWikiChanges` 仍为 false，生成候选不写 Wiki；M1 已验收的 source-only 导入可继续。

本地模型也要显式配置 endpoint 和 modelId，并通过同样的结构/质量测试。配置名称写 local 并不会自动安装模型。

### 7.2 隐私分批

第一轮只允许 5 份公开技术资料发送到指定模型。项目笔记和私密内容保持不可外发。编译选择混合资料而没有共同允许路线时，系统应阻止请求并说明原因。

预算采用你的明确确认值。方案中的单任务 $0.50、每日 $3、每月 $50 是示例上限，不是价格预测或推荐订阅费用。实际调用成本取决于模型、资料长度、重试和输出；必须可从任务日志复算。

### 7.3 第一份 Wiki 的生成与审核

选择同一主题的 1–3 份来源，点击“提出知识更新”。检查：生成页是否确有复用价值；标题是否过细；每个结论有没有来源；条件、版本和否定句是否保留；是否混入模型常识或自作主张的决策。

在 Pilot 的审核/冲突测试通过后开启 `writes.allowWikiChanges`；第一次最多批准 1 个新页，不做全量批量批准。批准前关闭目标编辑页；批准后核对文件和 provenance，再提一个直接问题和一个资料中无答案的问题。

### 7.4 提案审核标准

| 检查项 | 通过标准 |
|---|---|
| 定义/结论 | 能回答具体问题，不是换句话复述标题 |
| 来源 | 重要主张可点到固定原文，原文确实支持 |
| 范围 | 版本、时间、前提、例外没有被省略 |
| 人工内容 | 没有擅改你的决定或笔记 |
| 新建页 | 不能被已有概念页合理承载时才新建 |
| 差异 | 新资料带来的变化明确，不是无意义全文重写 |
| 隐私 | 输出不比敏感来源具有更宽的公开范围 |

审核不通过可以拒绝并记录原因；不能为了提高“自动化率”放宽来源校验。

### 7.5 M2 放行条件

至少 10 次真实编译提案、20 道真实问题经过人工检查；能区分 evidence不足与模型报错；一次引用注入和一次预算触顶被正确拦截；手改基线冲突保护通过；未批准候选不进入默认已审核 Wiki 查询。

## 8. 开发完成后的安装与启动

**本节命令是 E01–E14 要实现并验证的命令合同。当前方案包没有 `dist`、package.json 或可运行服务，不能直接执行本节。**

### 8.1 构建必须产生的文件

```text
dist/service/main.js
dist/cli/main.js
dist/plugin/main.js
dist/plugin/manifest.json
dist/plugin/styles.css      # 有样式时输出
```

在未来实现仓库根目录执行：

```bash
# [开发完成后执行]
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test:unit
pnpm test:integration
pnpm test:faults
pnpm build
```

任何一步失败都不复制插件到正式 Vault。native SQLite 依赖需在目标设备安装/构建验证，不能拿另一 OS 的 node_modules 直接复制使用。

### 8.2 初始化与只读启动

未来 CLI 应提供下列命令；执行者按 E14 实现这些旗标、帮助和错误返回，不用伪造成功输出：

```bash
# [开发完成后执行；配置文件为方案样例，初始化会产生唯一 vaultId]
node dist/cli/main.js init \
  --runtime-root "$HOME/.local/share/obsidian-kb" \
  --name Knowledge-Pilot \
  --config config/service.example.json

# init 输出实际 config 路径；下一行用该路径替换 CONFIG_PATH
node dist/cli/main.js doctor --config "$CONFIG_PATH"
node dist/service/main.js --config "$CONFIG_PATH"
```

`CONFIG_PATH` 是 init 实际输出值，不是照抄即可存在的默认文件。doctor 必须检查目录边界、SQLite/FTS、数据库完整性、对象权限、端口、模型配置和协议版本。未配置模型时只能判定“词法模式可用”，不得判定“AI 已就绪”。

### 8.3 安装自己构建的插件

官方 sample plugin 使用 `main.js`、`manifest.json` 和样式文件部署到 `.obsidian/plugins/<id>/`。[S09]

```bash
# [开发完成、全部测试通过后；从实现仓库根目录执行]
VAULT="$HOME/Knowledge/Knowledge-Pilot"
PLUGIN="$VAULT/.obsidian/plugins/personal-knowledge-bridge"
if [ -e "$PLUGIN" ]; then
  printf '%s\n' '插件目录已存在，请走升级/回滚流程，本步骤不覆盖。'
else
  mkdir -p "$PLUGIN"
  cp dist/plugin/main.js dist/plugin/manifest.json "$PLUGIN/"
  if [ -f dist/plugin/styles.css ]; then cp dist/plugin/styles.css "$PLUGIN/"; fi
fi
```

在 Obsidian 启用此本地插件，使用管理 CLI 的 `pair --config "$CONFIG_PATH"` 生成一次性配对码，在插件可信设置页输入。插件凭据存 Vault 外，不给其他 Agent 复制。

### 8.4 启用顺序

先只读连接 → Writer 验收后开启 `writes.enabled` 和 `allowSourceImports` → 导入 source-only → 离线搜索验收 → 配一个模型 → 生成但不应用提案 → 确认预算和隐私 → 开启 `allowWikiChanges`，仍逐提案批准 → 最后配置用户级自启动。

第一天不要同时开放云模型、自动写入、自动抓取和 MCP。否则出问题时很难定位边界，也无法知道哪一项授权导致副作用。

### 8.5 自启动要求

macOS 可用用户级 LaunchAgent，Linux 可用用户级服务管理，Windows 另设适配任务；这些是部署选择，不在本次包里交付未经验证的系统服务安装器。

自启动必须使用固定 Node 可执行路径、固定 config、受限日志目录；进程崩溃重启应退避；不能不断启动多个 Writer。服务启动先执行 migration 和 recovery 检查，无法验证 state.db 时拒绝写入。

## 9. 日常使用 SOP

### 9.1 收藏

只收藏预计会再次使用的资料；写一句“为什么保存”。确认正文和版本。放 Inbox 不代表立刻花模型费用。

### 9.2 导入

每日或积累少量后主动导入。先处理来源质量警告；重复资料只保留合理来源关系。来源能检索后，你已经可以工作，不必等待编译。

### 9.3 编译

围绕一个主题选择 1–3 份资料。优先更新已有页面，而不是给每篇文章生成三层目录。一次最多 1 新页、2 更新页；超过就拆批。

### 9.4 审核

先看变更原因，再看关键主张原文，最后看整页可读性。不能只看标题和“引用数量”。无法判断真伪的主张保持 draft/disputed，而不是为了归档写 reviewed。

### 9.5 提问与沉淀

查具体参数优先关键词和证据模式；做架构比较再用综合回答。重要输出至少抽查两个承重结论。仅保存会被再次使用的回答，且保存的是候选，不是新证据。

### 9.6 每周维护

查看 Inbox 积压、重复/过细页面、stale 结论、拒绝提案原因、模型费用和备份。选一个过期结论更新，选一份备份恢复验证。维护目标不是让页数持续增长，而是让知识更准确、更容易找到。

## 10. 故障处理手册

| 现象 | 先做什么 | 不要做什么 | 恢复成功的判据 |
|---|---|---|---|
| 搜索不到“权限” | 检查来源 lexicalReady、tokenizer 与实际 query terms | 立刻上向量库掩盖分词问题 | 固定短词测试可复现命中 |
| 编译没反应 | 查看 job stage、模型路线、预算、候选记录 | 重复点按钮制造多个任务 | 相同 idempotency key 仍指向同任务 |
| 模型超时 | 查看是否 outcome_unknown、保留预占 | 把失败记作零费用 | 下一次调用有独立 attempt 和预算 |
| 提案等待写入 | 打开 Obsidian，检查 bridge/epoch | 让服务直接写 Vault 绕开插件 | 批准/基线复验后继续 |
| BASE_REVISION_CONFLICT | 保留文件；比较人工版本；重新提案 | 用旧 afterText 强制覆盖 | 人工内容完整且新批准绑定新基线 |
| 文件写了一半 | 停止新提交，运行 reconcile，查看清单 | 手删 state.db 或整体回滚覆盖 | 全部 committed 或明确 conflict |
| 索引损坏 | 保留 state/objects，从空 index 重建 | 删除全部运行目录 | 同一来源与引用仍可读 |
| state.db 损坏 | 只读停写，恢复同一备份集 | 创建空库继续跑旧任务 | integrity/hash/恢复用例全部通过 |
| 发现错误结论 | 撤回相关来源/主张、标记页面复审 | 只改标题，保留旧答案默认可用 | 检索和上下文不再把它当有效依据 |
| 发现私密外发 | 停止模型调用、吊销相关凭据、登记影响范围 | 只删日志当作事故结束 | 关闭泄漏路径并重跑隐私测试 |

## 11. 备份、恢复与退出方案

### 11.1 备份范围

必须包含：Vault、state.db 一致快照、objects、policy/config、dependency baseline、backup manifest。模型密钥另走凭据恢复，不写进公开 ZIP。index.db 可以重建。

SQLite Backup API 提供一致备份路径；运行时不能仅复制主数据库文件忽略 WAL。[S10] 用户点击备份后，要显示 backupId、完整性结果与覆盖范围；失败要明确报错。

### 11.2 正式使用前做一次恢复演练

复制一个独立测试目录；停写；恢复内容与运行账本；重建索引；跑 20 道固定题中的 5 道；打开原文引用；检查一个未完成提案没有被错误执行。演练不在真实 Vault 上破坏性测试。

备份不等于同步：同步会复制误删，备份需要可回到指定点。第一版建议每日自动快照、至少每周抽查一次恢复；具体保留天数依据隐私政策和容量设置。

### 11.3 不想维护服务时怎样退出

关闭写入总开关和自启动；导出未完成提案及任务清单；做完整备份；卸载薄插件。来源与 Wiki 仍是 Markdown，可以继续在 Obsidian 使用。保留不可变来源和 provenance，不能只留下 AI 摘要。

不能把退出理解成删除 state.db：若还有已批准未提交或未知收费记录，先完成清算与清点。

## 12. 正式转入日常使用

### 12.1 按批量放大

先 30 份试点 → 100 份真实资料 → 300 份主题资料。每一批检查解析覆盖、重复提案、查询质量和费用。通过后再扩大，不用“能上传”当“能维护”。

最简单的正式路线是继续使用 Pilot 并重命名为日常知识库。已有大 Vault 可以先以选定文件导入，不必整体迁移。

### 12.2 接管已有 Vault 的专门检查

先做全量备份与 dry-run 清单；检查大小写/Unicode 路径碰撞、重复 pageId、受管路径冲突、wikilinks 和 embeds。人工目录不移动；自动化只进入用户批准的受管目录。

如果同名目录已经有人的笔记，换一个受管前缀，不自动接管。保留旧链接是迁移任务，不是随手 `mv`。源库 hash 清单与目标库对照，由你确认后才开放写入。

### 12.3 试点评分怎样计算

20 题不是统计上充分的大样本。对 17 个可回答问题，逐题登记去重的正确来源家族集合 G，以及检索 Top 10 命中的家族 H，单题 Recall@10=`|G∩H|/|G|`，报告 17 题平均值和每个失败题；无答案题不进入这一分母。跨版本/冲突题的 G 应包含所有必须展示的来源，不能只命中有利的一边就算完整。

3 个无答案问题要全部正确说明证据不足，才能达到这组小样本上“至少 90%”的门禁。还要同时报告可回答题是否被过度拒答，不能用全部拒答刷分。

重要主张支持率按人工标注计算：`被原文支持且未省略必要条件的主张数/被检查的重要主张总数`。报告实际分子/分母、条件遗漏和错误来源，而不只写一个百分比。机械引用可回读单独要求 100%，不能拿一个可打开链接抵消错误结论。扩大到 80 个真实问题后再作为模型升级基线。

### 12.4 上线放行表

使用 `templates/上线验收表.md`。必须包括：版本锁定、原始引用、中文检索、人工保护、审批身份、模型外发、预算、故障恢复、备份、撤回、插件卸载可读性。

任一隐私/内容保护失败，停写且不放行。语义质量不足可以保持 M1 词法资料库，不要求为了上线 AI 而降低门槛。

## 13. 与编码 Agent 协作的方法

每次只派发一个任务，附技术规范、任务条目、前置产物和失败用例。不要把“做完整知识库”作为一个不设边界的长任务。

可使用以下任务交接文本：

```text
阅读 docs/spec/01-Obsidian知识库技术方案.md 与任务 E05。
只实现本任务定义的 Writer 边界；不实现 Compiler，不修改人工目录。
先编写并运行基线冲突、回执丢失和第三种 hash 的失败测试。
实现后返回：修改文件、测试命令与真实结果、未覆盖场景、接口变更。
不得用 mock 结果声称真实 Obsidian 已测试，不得跳过失败测试。
禁止读取我的真实 Vault、模型密钥或其他项目；仅使用 fixtures。
```

示例中的 E05 是受控 Writer 任务；路径在实际仓库内按交付结构建立。编码 Agent 是否可访问真实资料由 OS/工具权限限制，不靠这一段提示词代替授权。

每完成一个任务，提交小范围 diff；只有验收通过才派下一个有依赖任务。遇到 SDK 行为不一致先记录 reproducer 和固定版本，不通过大规模重写掩盖问题。

## 14. 什么时候再加高级功能

| 触发事实 | 追加能力 | 不应触发的理由 |
|---|---|---|
| 固定题显示同义表达持续漏召回 | 向量或 QMD adapter | “大家都有向量库” |
| 经常有重要 PDF/图表无法进入资料层 | 受控解析 worker | “格式越多越显得完整” |
| 外部 Agent 重复询问同一知识 | 只读 MCP | “先暴露整个 Vault 所有写操作” |
| 已有明确公开内容和读者 | Quartz/PandaWiki 单向发布 | “顺便把私人库上线” |
| 两人以上需要共同维护 | 权威服务与团队 ACL，单独设计 | “共享文件夹就算协同” |

## 15. 第一轮执行清单

今天可做的工作是：打开 starter-vault；配置官方 Clipper；挑选 30 份资料；写 20 个真实问题；备份并标注哪些内容可外发。此时不需要服务器或模型调用。

进入开发时，从 E00/E01 开始。第一项演示目标不是 AI 自动写了多少页，而是“原文能被可靠保存、离线能搜到、一次人工修改不会丢失”。随后再开启知识编译和问答，最后通过恢复与预算门禁。

**最终交付应是一套你能每天使用、出错能解释、退出仍保留资料的知识系统，而不是一套只有作者会启动的演示工程。**
